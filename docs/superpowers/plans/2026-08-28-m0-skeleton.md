> - **Fonts needed a platform layer.** `tokens.js` holds the `@expo-google-fonts` file
>   names, which are correct on Android; iOS needs PostScript names, so `src/theme/fonts.ts`
>   maps them. Without it every font silently fell back to San Francisco on iOS.
> - **Expo SDK 57 does not compile under Xcode 26.3** without `patches/` — see
>   `patches/README.md`.

**Goal:** Turn this docs-only repo into an Expo app that runs as a dev build on a real iPhone and a real Android phone, wearing the Ponor identity from `DESIGN.md` §0, with lint, typecheck and tests green in CI.

**Architecture:** One Expo Router app at the repo root. The design tokens live in a single plain-JavaScript module (`src/theme/tokens.js`) that is the source of truth for *everything* — a Node generator script derives `global.css` from it, the Expo app config reads it, and TypeScript consumers import it through a hand-written `.d.ts`. That keeps colour values in exactly one place and makes the derivation testable, so the two themes can never drift apart. Depth-to-colour mapping is a pure function with no React or NativeWind dependency, so it can be unit-tested and reused later by charts, map pins and SVG.

**Starting point (discovered in Task 1):** the SDK 57 `create-expo-app` template is not a bare skeleton — it ships a tab-based demo app with its own colour system (`src/constants/theme.ts`, `src/hooks/use-theme.ts`, `src/global.css`), Expo-branded assets, and demo components. Task 1 reduces it to a single route at `src/app/`, because a second source of colour truth would contradict the Global Constraints below, and the tab bar is explicitly out of M0 scope. Routes therefore live at `src/app/`, not `app/`.

**Tech Stack:** Expo SDK 57 (React Native 0.86, React 19.2) · TypeScript · `expo-router` · NativeWind v5 (preview, CSS-first) + Tailwind v4 · `expo-font` config plugin with `@expo-google-fonts` · Jest via `jest-expo` · ESLint via `eslint-config-expo` · GitHub Actions.

## Global Constraints

- **Colour is depth, and colour is nothing else** (§0.1). Controls are monochrome; the primary button is inverted ink. Never use a depth colour for chrome.
- **Depth scale, dark** (bands 1–6): `#FF6B4A` `#FF9F43` `#F5CE3E` `#3FCB94` `#2E9BE0` `#6673E4`
- **Depth scale, light** (bands 1–6): `#E04A28` `#C2600A` `#8F7000` `#0E9F6E` `#0B76B8` `#3A49C0`
- **Depth bands:** 0–6 m · 6–12 m · 12–20 m · 20–30 m · 30–40 m · 40 m+. A depth exactly on a boundary belongs to the *shallower* band.
- **Theme tokens, dark:** `bg #080B0F` · `surface #111820` · `border #212D38` · `fg #F0F5F8` · `fgMuted #7C8D9A` · `action #F0F5F8` · `actionFg #080B0F`
- **Theme tokens, light:** `bg #EDEEEA` · `surface #FFFFFF` · `border #CDD3CC` · `fg #0D1216` · `fgMuted #5A6670` · `action #0D1216` · `actionFg #EDEEEA`
- **Both themes ship in M0.** The app follows the OS colour scheme. When the OS reports no preference, fall back to **dark**.
- **Type:** Archivo for UI (400/500/600/700), IBM Plex Mono for all data (400/500/600). Data uses tabular figures.
- **Tap targets never below 48 dp.** Primary action sits in the bottom third.
- **Build against token names, never colour literals** (`CLAUDE.md`). A hex code in a component is a review failure.
- **No profile curves** (§0.4). Nothing in M0 draws a dive profile except the app icon.
- Commit messages are plain — no ticket keys. This is not a work repo.

- [ ] **Step 5: Write the implementation**

Create `src/theme/depth.ts`:

```ts
import { depthBandLimits, depthScale, type ColorScheme } from './tokens';

export type DepthBand = 1 | 2 | 3 | 4 | 5 | 6;

/**
 * Which depth band a dive falls in. A depth exactly on a boundary belongs to
 * the shallower band, so a 6.0 m dive is band 1 and a 6.1 m dive is band 2.
 */
export function depthBand(metres: number): DepthBand {
  if (!Number.isFinite(metres) || metres < 0) {
    throw new RangeError(`depthBand: expected a non-negative depth in metres, got ${metres}`);
  }
  const index = depthBandLimits.findIndex((limit) => metres <= limit);
  return (index === -1 ? 6 : index + 1) as DepthBand;
}

/** The colour that encodes this depth in the given scheme. */
export function depthColor(metres: number, scheme: ColorScheme): string {
  return depthScale[scheme][depthBand(metres) - 1];
}
```

- Produces:
  - `src/theme/css.js` exports `assertHexColor(hex: string): string` and `buildThemeCss(): string`
  - Tailwind colour classes `bg-bg`, `bg-surface`, `border-border`, `text-fg`, `text-fg-muted`, `bg-action`, `text-action-fg`, and `text-depth-1` … `text-depth-6`, all resolving per-scheme

**Read this before you start — NativeWind v5 is not NativeWind v4.** The installed stack is `nativewind@5.0.0-preview.4` on `tailwindcss@4.3.3`, and Tailwind v4 is **CSS-first**:

- **There is no `tailwind.config.js`.** Do not create one. `nativewind/preset` is not an exported subpath — `require('nativewind/preset')` throws `ERR_PACKAGE_PATH_NOT_EXPORTED`, and nothing in the toolchain reads a JS Tailwind config.
- The theme lives in `global.css` in an `@theme` block. Tailwind generates `bg-bg` from `--color-bg`, `text-depth-3` from `--color-depth-3`, and so on.
- Dark mode is **`@media (prefers-color-scheme: dark)`**, which NativeWind maps to React Native's `Appearance` API automatically. Redefining the custom properties under that media query is all the theme switching this app needs — no provider, no context, no JS.
- Colours are written as **plain hex**. Tailwind v4 handles opacity modifiers with `color-mix()`, so the old `rgb(var(--x) / <alpha-value>)` triplet trick is unnecessary and actively degrades here.

```js
const { tokens, depthScale } = require('./tokens');

const HEX = /^#[0-9a-fA-F]{6}$/;

/** Guards against a malformed token reaching the stylesheet. Returns the colour unchanged. */
function assertHexColor(hex) {
  if (typeof hex !== 'string' || !HEX.test(hex)) {
    throw new TypeError(`assertHexColor: expected a six-digit hex colour, got ${hex}`);
  }
  return hex;
}

const CAMEL_TO_KEBAB = /[A-Z]/g;

function varsFor(scheme, indent) {
  const lines = [];
  for (const [name, hex] of Object.entries(tokens[scheme])) {
    const kebab = name.replace(CAMEL_TO_KEBAB, (c) => `-${c.toLowerCase()}`);
    lines.push(`${indent}--color-${kebab}: ${assertHexColor(hex)};`);
  }
  depthScale[scheme].forEach((hex, i) => {
    lines.push(`${indent}--color-depth-${i + 1}: ${assertHexColor(hex)};`);
  });
  return lines.join('\n');
}

/**
 * The whole of global.css, derived from tokens.js. Never hand-edit global.css.
 *
 * Tailwind v4 is CSS-first: the @theme block is what generates the utility
 * classes (--color-bg becomes bg-bg, --color-depth-3 becomes text-depth-3).
 * Redefining the same custom properties under prefers-color-scheme is the
 * whole of theme switching — NativeWind maps that media query to React
 * Native's Appearance API, so no provider or JS is involved.
 */
function buildThemeCss() {
  return `/* GENERATED by scripts/build-theme-css.mjs from src/theme/tokens.js — do not edit. */
@import "tailwindcss";
@import "nativewind/theme";

@theme {
${varsFor('light', '  ')}
}

@media (prefers-color-scheme: dark) {
  :root {
${varsFor('dark', '    ')}
  }
}
`;
}

module.exports = { assertHexColor, buildThemeCss };
```

- [ ] **Step 3: Write the implementation**

Create `src/theme/resolve.ts`:

```ts
import { tokens, type ColorScheme, type ThemeTokens } from './tokens';

export type SchemePreference = ColorScheme | 'system';

/**
 * Whatever the OS reports. React Native 0.86's `useColorScheme()` returns
 * `'unspecified'` when the platform has no preference — it does not return
 * null, though `Appearance.getColorScheme()` still can.
 */
export type SystemScheme = ColorScheme | 'unspecified' | null | undefined;

/**
 * Which scheme the app should render in. Ponor is dark-first, so anything that
 * is not an explicit light or dark preference resolves to dark.
 */
export function resolveScheme(
  systemScheme: SystemScheme,
  override?: SchemePreference,
): ColorScheme {
  if (override && override !== 'system') return override;
  if (systemScheme === 'light' || systemScheme === 'dark') return systemScheme;
  return 'dark';
}

export function themeFor(scheme: ColorScheme): ThemeTokens {
  return tokens[scheme];
}
```

- [ ] **Step 1: Write the mark**

Create `assets/mark.svg` — the dive profile from `DESIGN.md` §0.3, on the dark ground so it reads on any home screen:

There is no background rectangle — `build-icons.mjs` paints the ground from `tokens.dark.bg`, so the icon background stays tied to the token. The gradient stops below are deliberate exceptions: this file is the design source for the mark itself (`DESIGN.md` §0.3), not runtime UI colour.

**The geometry below is not arbitrary — it took four rounds of rendering and looking.** Two things matter and are easy to lose:

- **The profile must not return to the surface.** An earlier version descended, ran along the bottom, and climbed back to the waterline. Closed at the top by the surface line, with two similar diagonal walls, it read unmistakably as a *bucket*. Ending the ascent in open space removes the second wall and the container reading goes with it.
- **The surface is a wave, not a line.** A straight bar reads as a rim or a lid; a wave reads as water immediately, and that single change does more for legibility than any amount of stroke tuning.

```svg
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 64 64" width="1024" height="1024">
  <defs>
    <linearGradient id="depth" gradientUnits="userSpaceOnUse" x1="0" y1="15" x2="0" y2="46">
      <stop offset="0" stop-color="#FF9F43"/>
      <stop offset="0.45" stop-color="#3FCB94"/>
      <stop offset="1" stop-color="#2E9BE0"/>
    </linearGradient>
  </defs>
  <path d="M2 15 q 5 -3.6 10 0 t 10 0 t 10 0 t 10 0 t 10 0 t 10 0"
        fill="none" stroke="#5A6C78" stroke-width="2.4" stroke-linecap="round"/>
  <path d="M12 15 L19 46 L28 46 L34 34 L44 34 L50 24 L54 24"
        fill="none" stroke="url(#depth)" stroke-width="4.6"
        stroke-linecap="round" stroke-linejoin="round"/>
</svg>
```

The wave's amplitude is tuned for small sizes: finer ripples blur into a fuzzy bar by 32 px, and a longer swell stops registering as water at all. The ascent ends at `x=54` rather than further right so the final step stays inside Android's 66 % adaptive-icon safe zone.

Create `scripts/build-icons.mjs`:

```js
import { createRequire } from 'node:module';
import fs from 'node:fs';
import path from 'node:path';
import { fileURLToPath } from 'node:url';
import sharp from 'sharp';

const require = createRequire(import.meta.url);
const { tokens } = require('../src/theme/tokens.js');

const root = path.join(path.dirname(fileURLToPath(import.meta.url)), '..');
const svg = fs.readFileSync(path.join(root, 'assets', 'mark.svg'));
const out = path.join(root, 'assets', 'images');
fs.mkdirSync(out, { recursive: true });

const targets = [
  // Full-bleed store and home-screen icon.
  { file: 'icon.png', size: 1024, pad: 0 },
  // Android masks the outer ~33%; 112 px keeps the mark inside the safe zone without shrinking it to a dot.
  { file: 'adaptive-icon.png', size: 1024, pad: 112 },
  // Splash art is composited on a flat background by expo-splash-screen.
  { file: 'splash-icon.png', size: 512, pad: 96 },
];

for (const { file, size, pad } of targets) {
  const inner = size - pad * 2;
  const mark = await sharp(svg).resize(inner, inner).png().toBuffer();
  await sharp({
    create: { width: size, height: size, channels: 4, background: tokens.dark.bg },
  })
    .composite([{ input: mark, top: pad, left: pad }])
    .png()
    .toFile(path.join(out, file));
  console.log(`wrote assets/images/${file} (${size}px)`);
}
```
