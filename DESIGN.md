# Ponor — Design Plan

> **v1 scope · rev 5 · 2026-08-28**
> Core decisions: **Supabase** backend · **offline-first** · **optional sign-in** · photos in **v1.1**
> Name and visual identity locked in §0; both themes ship from M0.
> Styled copies of this document and of the visual identity live as Claude artifacts; their links are kept out of this public repo.

A free, offline-first dive log for iPhone, Android, and tablets — web to follow — that *fills itself in*: after the first dive of a trip, you only touch what changed.

---

## 0. Name & visual identity

**The app is called Ponor.** In Czech, *ponor* is the submersion itself — the draft of a vessel, how deep a thing sits; the root of *ponořit se*, to submerge. In English it is a karst term: the opening where a surface stream leaves the daylight and becomes a subterranean river. The same meaning in both languages, the same pronunciation (PO-nor), it declines cleanly in Czech, and it spells itself when heard. **`ponor.app` and `ponor.online` are registered.**

Checked and rejected on availability: *Slate*, *Bezel*, *Sextant* (crowded on the App Store), *Halocline* (Halocline GmbH holds software-class trademarks), *Atoll* (Forsk's registered software mark), *Manta* (an existing paper dive logbook), *Deco* (TP-Link, plus an existing dive-planning app). Note that every competitor is a dive+log mashup — Dive Log, Diving Log, Divog, Diviac, DiveMate, Diveboard, Depth, Subsurface — so a name in a diver's own vocabulary stands apart by default. Still outstanding: a direct App Store and Play Store search, and a trademark register check.

### 0.1 Colour is depth, and colour is nothing else

Water strips colour out in a fixed order — red is gone by about 5 m, then orange, then yellow, then green; blue is what is left. The depth scale **is** that sequence, so a depth always carries a colour and the colour is physically true.

| Band | Dark | Light |
|---|---|---|
| 0–6 m | `#FF6B4A` | `#E04A28` |
| 6–12 m | `#FF9F43` | `#C2600A` |
| 12–20 m | `#F5CE3E` | `#8F7000` |
| 20–30 m | `#3FCB94` | `#0E9F6E` |
| 30–40 m | `#2E9BE0` | `#0B76B8` |
| 40 m + | `#6673E4` | `#3A49C0` |

Because colour is spoken for, **every control is monochrome** — the primary button is simply inverted ink. Depth is always redundantly encoded by the number itself, so the scale never carries meaning on its own: colour-blind safe, and legible in glare.

### 0.2 Theme tokens

Both themes ship from M0. The app follows the OS and the choice is overridable in settings; components read whichever token set `resolveScheme` returns, so the same component serves both.

| Token | Role | Dark | Light |
|---|---|---|---|
| `bg` | App ground | `#080B0F` | `#EDEEEA` |
| `surface` | Cards, fields, charts | `#111820` | `#FFFFFF` |
| `border` | Hairlines, dividers | `#212D38` | `#CDD3CC` |
| `fg` | Text and values | `#F0F5F8` | `#0D1216` |
| `fg-muted` | Labels, units, metadata | `#7C8D9A` | `#5A6670` |
| `action` / `action-fg` | Primary button — inverted ink | `#F0F5F8` / `#080B0F` | `#0D1216` / `#EDEEEA` |
| `depth-1…6` | Depth scale — **data only, never chrome** | see §0.1 | see §0.1 |

**Type:** *Archivo* for UI and display, *IBM Plex Mono* for all data — depths, pressures, durations, timestamps — with tabular figures wherever digits align in a column. Both carry Latin Extended, which Czech needs (ě š č ř ž ů). The wordmark is Archivo, uppercase, tracked +0.2 em, following the vernacular of dive-instrument brands.

### 0.3 The mark

A dive profile under a wavy surface: a steep descent, bottom time, then a staged ascent that ends in open water rather than climbing back to the waterline. Both of those are load-bearing, and it took four rounds of rendering to find out why. A profile that closes at the top against a straight surface line reads unmistakably as a **bucket** — two matching diagonal walls over a flat base. Ending the ascent in open space removes the second wall; making the surface a wave says "water" instantly. Stroked in the depth gradient, flat single-colour below ~32 px, and the same shape the app will draw for an imported dive — so the icon is a sample of the product rather than a badge stuck on it.

The gradient stops are read from `depthScale.dark` at build time, so the mark cannot drift from the palette. The wave itself is stroked `#5A6C78` — deliberately **not** a theme token. It is a brand-asset colour belonging to the mark alone, chosen to sit quietly behind the profile on the icon's dark ground; it is never used in the interface, where `fg-muted` serves that role.

### 0.4 Profiles are drawn only from real data

A dive row shows the **coloured depth number and no graphic**. When a dive has a real sample series — post-v1, from a UDDF / Subsurface / FIT import — that same row grows a profile sparkline and the dive detail gains a profile chart, automatically and without a redesign. The app never draws a schematic curve interpolated from max depth, average depth and duration: an invented shape on a dive log reads as recorded data, and it isn't.

That claim was checked rather than assumed (design pass after M1b): the chart occupies the space between the detail hero and the first cluster, which is empty today, and nothing above it moves. **The curve is stroked through the depth gradient** — a profile is depth against time and colour already encodes depth, so the chart's colour is data under the same rule as everything else, and the chart becomes the same object as the mark in §0.3. In a row the sparkline stays **monochrome**: the number already carries the colour there, and at 46 px a gradient reads as a smudge, so the sparkline contributes shape and the number magnitude. A row without samples shows no sparkline and no placeholder, exactly as a dive without a depth shows no number.

### 0.5 Constraints the design must answer

- **Sunlight.** Dives are logged on an open deck at noon. The light theme exists for this; contrast is a functional requirement, not a taste question.
- **Wet hands, one thumb.** Tap targets never below 48 dp, and the primary action sits in the bottom third of the screen.
- **Czech runs 20–30 % longer** than English. Labels wrap to two lines rather than truncate.

### 0.6 Screen composition

Designed after M1b, once the built screens showed the tokens being *obeyed* without being *used* — every element the same size, and the depth colour reduced to a small number at the end of a row. The rule below is what makes the palette legible.

**Search and `+` share one capsule at the top right.** It began at the bottom — measured off iOS 26 Messages, and correct while Ponor had no tab bar — and moved when the tabs arrived and claimed that strip (§3). The capsule follows Calendar: one rounded glass container, magnifier and `+` inside it as **equal monochrome glyphs**, no border and no rule. Liquid Glass where the device has it (`expo-glass-effect`, guarded by `isLiquidGlassAvailable()`), a plain `surface` capsule everywhere else — which is the common case and must look deliberate rather than degraded. The `+` gets **no extra emphasis** over the magnifier: §10 already rules out a hue, and size or weight would reintroduce the "is this data or chrome" question §0.1 exists to prevent.

**The magnifier is a trigger, not a field.** Tapping it opens a full-screen search whose input is docked at the **bottom, on the keyboard**, with the list cleared to results and a visible way out — measured off Messages, which anchors its field at the bottom rather than moving it to the top when search is entered. A field under the header would put the input as far from the thumb and the keys as the screen allows; that arrangement was rejected once already for being the brightest object in the app, and again for this.

**The Dives screen is a native large-title screen, and the capsule floats beside the title.** Measured off iOS 26 rather than recalled, and it took four shapes to get here. The large **"Dives"** title sits at the same height as every other screen's title — the safe-area inset plus the ordinary heading padding, through the one `screenTopInset` every screen root asks the device for (§4.1) — and the search-and-`+` capsule **floats to its trailing side, over the scroll content**, rather than occupying a bar of its own above it. The shared `screen` style deliberately carries no `paddingTop`, so a root that forgets to compose the inset fails visibly rather than quietly rendering slightly too high. **No compact title fades in when the title scrolls away**: the tab bar already shows which screen is selected, so the screen is never unidentified, and a scroll-driven crossfade is machinery with an edge case at every rubber-band.

**The title says what the logbook adds up to** (M1l, the owner's design sheet). Under "Dives", in muted mono: `128 dives · 96 h 12 min · deepest 41.2 m`. Four things about it are rules rather than styling. **The three figures are §3's Stats tab**, word for word, so they have one owner (`domain/logbookStats.ts`, §4.1) and M3 renders them rather than recomputing them. **Planned dives are excluded**, as §2.4 already requires of anything called stats — they have no duration and usually no depth, and would drag every figure. **All three describe the same population: the logbook, never `dives_before`** — a diver with 100 pre-Ponor dives has a top row reading `#128` above a list of 28, and a header saying `128 dives · 3 h` would be summarising two different populations in one line; §2.5 owns the numbering, and this line summarises *the list beneath it*. **The depth takes no band colour**, though it is a depth and §0.1 says colour encodes depth: this figure is an aggregate over many dives, so any one band would be a claim about a set that no band is true of. A figure with nothing behind it is **omitted, not drawn as an em dash** — the dash belongs to a labelled row that is drawn whether or not it holds a value, and this line has no labels.

**And the line is why the header column stops short of the capsule** (M1l, found by looking, not by a test; corrected M1m). The summary runs toward the floating capsule and reaches it: at eight dives it stops 10 pt short of the glass, and at the sheet's own three-digit example it renders *behind* it. **The header's text column is therefore capped at the capsule's leading edge**, and the summary wraps to a second line under it — which is what the owner's sheet draws, `128 dives · 96 h 12 min ·` above `deepest 41.2 m`, and the wrap lands exactly where the capsule begins.

  **Capping the width alone is not enough, because a fold goes wherever width runs out.** Capped and left to wrap naturally the line broke as `8 dives · 5 h 19 min · deepest 41.2` above a second line holding nothing but `m` — every space is a break opportunity, so the figures tear before the separators do. Each figure's own spaces are therefore unbreakable and **the middots are the only folds**, which is what makes the sheet's break reproducible rather than a coincidence of one dive count. It also means `0 dives` can never break at all.

  M1l reserved the capsule's **height** instead, pushing the summary down the page, and rejected the width with arithmetic: 257 pt of remaining room for a line already 255 pt long. **That arithmetic was right and answered the wrong question** — it assumed the line had to fit on one, and the design never asked it to. The owner caught it the way he catches all of these, by holding the sheet beside the screen: the gap under the title was wrong, and the reserved height was what made it wrong. A constraint that buys its clearance out of *vertical* space, on a screen whose title is the thing being measured, will always show up as the title looking wrong.

**The app has one content column** (M1l, owner's call: *"there is no reason to have them different"*). Every screen's title, rows, hairlines and cluster labels hang off one inset — `CONTENT_INSET`, one constant read by the list, the form, the dive detail and Settings. There were two, 16 and 20, and the 20 was the form's: it had a real job once, holding room for the old `carried ×` chip's outward tap slop, and **M1h retired that job without retiring the number**. What was left justified 20 by pointing at the detail screen's 20. The owner found the survivor the way these are always found — by putting two screens side by side and seeing the titles disagree — and the same screen had already recorded the same complaint in M1d, when the detail back control sat 4 px inboard of the title directly beneath it. One column, named for the rule rather than for the form that used to own it.

**The capsule floats, and the sticky trip header is what gave way.** The owner's argument is that at rest a floating capsule covers nothing — it sits beside the title, in the space a title leaves empty — and a row passing under it while scrolling is recoverable, because you scroll on. That is right about rows and **wrong about a sticky header, which parks under the capsule for a whole trip's scroll extent instead of passing beneath it**; that is exactly how a trip's trailing date range came to be observed clipped to `…16`, twice. So **trip headers scroll like everything else** (§10). The shapes before this were a pinned bar holding title and capsule together — which cost the title the height every other screen's title has, and is what this replaces — and before that a capsule that receded on scroll, which worked and hid the `+` precisely when a diver deep in a long logbook wanted it. `useHideOnScroll` existed only for that and went with it.

**A field's label clears its rule by the same margin whether its value trails or stacks.** Found on Settings, where `Units` sat visibly tighter under its hairline than `Dives before Ponor` did. The cause was not what it looked like: the 48 dp tap floor sat on the input, and a label was positioned by centring within it — so a field whose value *trails* got the floor's leftover as clearance, while one whose value *stacks* (chips, notes, an open picker) already exceeded 48 dp, the centring became a no-op, and the row collapsed to the label's own height. The floor belongs on the row, not the input. The same correction reaches the form's own `Entry`, `Salinity` and `Water body` labels.

**Depth is the anchor of a dive row.** It is the value that actually differs dive to dive — a trip is four rows all saying "Blue Hole" — and it is the one the palette exists to encode. It is set in IBM Plex Mono Medium at 20 px (34 px on dive detail), in its band colour, right-aligned with tabular figures so a column of dives has a column of aligned decimals. Nothing else in a row gains colour.

| Element | Face | Size | Treatment |
|---|---|---|---|
| Depth value | Plex Mono Medium | 20 / 34 | Band colour, tabular, right-aligned |
| Site name | Archivo Medium | 16 | Wraps to two lines, never truncates |
| Trip header | Archivo SemiBold | 11.5 | Uppercase, +0.13 em, muted; date range in mono, trailing |
| Dive number | Plex Mono | 11 | Muted, above the site name — a label, not a headline |
| Row metadata | Plex Mono | 11.5 | Time · duration · rating, middot-separated |
| Cluster label | Plex Mono | 10.5 | Uppercase, +0.14 em, muted |
| Computed value | Plex Mono | 13.5 | Muted ink, `=` prefix in a fixed-width slot before the value |

**Computed values are marked as computed.** Every value the app derives rather than the diver enters — time out, surface interval, used pressure, gas used, RMV and MOD — is prefixed with a muted `=` and sits in muted ink. The mark is an equals sign because that is literally what the value is: the result of a calculation, not something anyone typed. An earlier version used a small outlined square, which read as a rendering artefact rather than a deliberate mark — a symbol that needs a legend has already failed. A diver should never have to wonder which numbers came off their computer and which the app worked out. The rule is *derived or entered*, with no exception for arithmetic simple enough to do in your head: used pressure is start minus end, and it is marked for the same reason RMV is. Anything in `src/domain/derived.ts` is marked.

**Carry-over marks what it inherited, and says when you threw it away** (rewritten M1h, the owner's design). A prefilled field carries a **drawn return mark and a clear control, grouped together at the row's trailing edge** — the ring a glyph in a real 48 dp box, not a small mark with slop bolted on. **The mark sits with the ring rather than beside the value, and that is the whole rule**: led by the value it would trail the *label* instead, landing at a different x on every row, and it was built that way first and measured ragged — `↵` at 65 pt on one row and 84 pt on the next. Grouped at the trailing edge it is one column at 326 pt across text rows and chip rows alike, which is what the chip rows already did. One placement for the whole form rather than two. Accepting costs nothing: no confirmation, no tap. Overwriting is just typing, and drops the mark. The clear control empties the field to a real blank, **never a zero** (§10), and the row then reads `— cleared` in muted mono.

  **That third state is the point.** Before this a cleared field and a never-carried field were the same blank row, so a diver who deliberately threw away a carried buddy could not tell that from the form simply not having one — the app knew a fact it did not show. Chip groups carry one clear for the whole group, since a chip row has no per-value trailing edge to hang one on. The header says what was inherited and from which dive.

  **Two things this paragraph used to claim and should not have.** It described the chip treatment as `carried ×`, which M1h replaced. And it said *"the form header's 'from #6' is tappable and starts the dive blank"* — **that control has never existed**, in any milestone; the only occurrences of the phrase in the source are comments quoting this sentence. It is not built and is not planned here; the header line is a caption, and if a start-blank affordance is ever wanted it is a new decision rather than the completion of an old one. Recorded rather than quietly deleted, because a spec asserting an unbuilt feature is the same drift §10 caught twice this milestone, and this one survived four.

**Chrome the type scale does not cover.** Hairline separators on `border` divide dive rows, **set on each row's top edge, not its bottom**. That is not interchangeable: a top edge puts a line under the trip header, where the design wants one, while a bottom edge puts every line one position later and leaves the header touching its first row. The last row of a group therefore carries no line beneath it — groups are separated by the next header's own top padding, not by a rule. Without any of this the list is one undifferentiated column. The day strip's action is a bordered pill in tracked uppercase, not plain text, so it reads as a control rather than a label. The dive-detail back control is mono, muted and small — it is a way out, not a heading. Rating marks are **drawn**, not typed: `●` and `○` are different sizes in almost every typeface, so a rating rendered from glyphs looks broken; draw both as circles of one diameter, filled or outlined. **Leaving a screen has one treatment everywhere** — the dive-detail back control's mono/muted/small form is also the form's way out (`‹ Cancel`), so "this takes you back" reads the same wherever it appears and never competes with the primary action beneath it. A form with no visible way out was shipped once and only found by using the app: swipe-back worked, so every test passed and nothing on screen said you could leave. **"Up next" is a section header but not a trip,** so it takes full `fg` where a trip's title is muted, and puts its dive count in the same trailing slot, same mono face, that a trip fills with its date range — an empty slot there read as a date range that had failed to load. Ink versus muted ink is the only lever: §0.1 rules out a hue, and a new shape would be new vocabulary for one header. **The dive-detail back control aligns to the hero's own 16,** and the hero's top padding drops to 4: the control keeps its 48 dp tap-target floor (§0.5), and without that trim the floor's leftover slack and the hero's padding stack into a visible gap between the way out and the title.

**A control that is about the primary action is drawn with it, not at the end of the content** (M2f). §0.6 already places a *deliberate act* — *Delete dive*, *Delete preset*, *Save as preset* — at the end of a screen's content, where it takes a reach. **That position is for an act on the page's object.** A control that changes what the *button* does belongs in the button's own block: the account screen's sign-in/sign-up toggle shipped at the end of the content and read as orphaned — 150 pt below the last row with 400 pt of empty screen beneath it, and centred while every other element was left-aligned on the content inset, which is a second idiom for one control. Centring is coherent under a full-width button and was not coherent alone in the page body. The one destructive control on that same screen stays at the end of the content, and that is the distinction rather than an exception to it: **sign-out acts on the account, the toggle acts on the button.**

**Hand-ordering lives on a day strip, not a row.** A trip spans several days but only one may be reorderable, so a control on the trip header would be ambiguous. Days that qualify get a strip — `18 Aug · 2 dives, no times` — which also states *why* they qualify; without it a diver who adds a time watches the control vanish for no visible reason. Entering the mode dims the rest and puts the arrows in the slot the depth value occupies, so row heights do not change.

**The form is the dive detail you can type into** (designed after M1d, for the same reason the rest of §0.6 was designed after M1b: the screen was built to §2.2's structure and then styled by default, and it ended up speaking a different visual language from the rest of the app for identical content — a depth typed in Archivo and read back in Plex Mono). The form borrows the detail screen's grammar rather than inventing one:

- **A field is a row, not a box.** Label at the leading edge in Archivo 15 muted — the detail screen's own row label — and the value trailing. Separated by a hairline on each row's **top** edge, the same rule dive rows follow. Five bordered boxes down the core strip was the heaviest chrome in the app, drawn in advance for every field whether or not it was being used.
- **Figures in mono, names in sans.** A depth, duration, pressure or temperature is a data figure and takes Plex Mono 15 with tabular figures (§0.2); a site, centre or buddy is a name and stays Archivo. The unit follows the figure as a muted suffix, exactly as `12.2 m` reads on the detail, and an empty numeric field shows that unit as its placeholder so the row still says what belongs in it.
- **Focus is what draws the affordance.** The focused row fills with `surface`; nothing else does. The box appears where it is wanted instead of five times over.
- **A group header is a cluster label** — Plex Mono 10.5, uppercase, +0.14 em, muted. *Conditions* and *Gas & cylinders* name the same groups on both screens and used to carry two different treatments.
- **A field error is text, not a field.** Muted, trailing, under the row it belongs to. Shipped once as a white rounded box the same height as an input, which read as a second empty field rather than a message.
- **Autocomplete's position is fixed here; its styling is not.** The list belongs directly under the focused row. How it looks waits for M2, which reworks site search around the shared site database and adding new sites — designing it now means designing it twice.

**The empty logbook is the one screen that can teach §0.1** (M1h, the owner's design). It said "Your logbook is empty." over a button — the only thing it had to say, and nothing a diver did not already know. Meanwhile the rule the whole palette rests on was explained **nowhere**: a diver met the depth colours one number at a time at the right-hand end of a dive row, where a colour that happens to vary looks like decoration. This is the only screen with **no dive to attach a colour to**, so it is the only place the scale can appear *as a scale*, and it is the last time it is seen out of context. Top to bottom, left-aligned in the app's one content column (§0.6's `CONTENT_INSET`): the large title with **"0 dives"** beneath it in muted mono — which is also what tells this branch apart from the one that has not read the logbook yet — then the mark at 120, `NOTHING LOGGED YET` in the cluster label, §1's *works at sea* said to a diver rather than to a planner, **six bars in the six band colours with their ranges beneath**, and two mono lines giving the rule its reason: colour is depth, and water strips warm light first.

  **The prose takes a measure, and the mark takes its air below rather than around** (M1l, owner's call). Both prose blocks are capped at a reading width instead of running the full screen; a long line of 11 pt mono edge to edge reads as a paragraph of terms and conditions, which is the opposite of what a first-run screen is for. The measure is a width, never a hand-placed line break — Czech runs 20–30 % longer (§0.5) and would break anywhere a break was put. The extra clearance under the mark is set **on the mark**, not by widening the block's rhythm: the block is centred, so a bigger shared gap moves everything and closes nothing in particular.

Three things about it are load-bearing rather than stylistic. **The mark is monochrome here, and that is §0.1 enforcing itself** — §0.3 strokes it in the depth gradient on the *icon*, but on screen a gradient mark would be colour spent on brand, so the only hue anywhere on this screen belongs to the legend, and the legend is depth. **Every number comes from `theme/depth.ts`**, the bars' ranges and the two figures in the reason line alike; a legend that retypes a boundary is the drift §4.1 exists to stop, and it was already visible before it was fixed — bars reading `0–20 … 131+ ft` under a caption saying "6 m". And **the labels follow the diver's units**, ragged feet included, because a first-run screen that quietly switched unit systems would be a strange thing to teach on.

**Option chips and the group header** (owner's calls, after seeing the form built):

- **A chip is filled.** `surface` behind an unselected chip, `action` ink behind the selected one — the same invert the save control uses, so "the chosen thing is the inverted thing" is one rule across the app. This does put a `surface` fill on two different things (a chip, and the focused row); they are told apart by shape and scale rather than by colour, a small pill inside a row against a full-bleed fill. Recorded as a known trade-off, not an oversight.
- **An icon appears only where the value has one, and the test is whether the mark carries the meaning or merely labels it.** *Shore* and *boat* pass trivially. The first version of this paragraph ruled out the scales — salinity, suits, cylinder materials — on the grounds that drawn as icons they collapse into near-identical droplets and suits separated by tally marks, which is a legend, and §10's computed-value square is the precedent: a symbol that needs a legend has already failed. The icon **supplements the label rather than replacing it** — never an icon alone. **Only *Entry* carries marks today**; every other chip row is bare.

  **M1h gave the scales marks that passed this test on paper, and M1i took them out after seeing them.** They were not arbitrary glyphs: current arrows accumulated one way, surge two ways, visibility bars counted up, weather took SF Symbols' own skies — each encoding its scale in itself, which is exactly what the paragraph above asks for. **They came out on measurement, not on principle** (owner's call): each arrow cost ≈29 px, which pushed *Current* and *Surge* onto a second line that they clear comfortably without one, and *Visibility low* — a single bar at that size — read as **punctuation**, a full stop sitting in front of the word. A mark that passes the meaning test and still costs a row its line has failed a test the paragraph did not name. **The intent survives on §9's shelf as a drawn set of our own**, which is the owner's actual objection: SF Symbols is not this app's hand. Do not restore these from the shelf one row at a time — a set is the point.

  One argument from that round is worth keeping, because it is the reasoning any replacement has to survive: **Waves shipped bare even when the others had marks.** Repetition encodes *frequency*, not amplitude, so a counted Waves would have made Waves, Current and Surge three rows of "three of something"; and the only working amplitude encoding was Visibility's bars, which reused would have made **both** rows a legend. There was no mark that carried the meaning, so there was none — the rule applied against its own convenience, which is the hard direction.

  **A mark takes the ink of the label beside it, handed out by the chip.** `OptionChips` knows whether it is selected and therefore what ink its label is about to wear; the mark is given that value rather than choosing one, which is what makes a mark invert with its chip instead of vanishing on it. Still live, with `EntryIcon` as its one caller. The rule's second half — that a **drawn** mark resolves that ink back to a sheet style rather than painting it directly, since §4.1 gives `theme/styles.ts` every token-to-property binding — lost its call site when the scale marks went and holds again the moment §9's set arrives.

  **The drawn rating now has two homes and stays one component.** §0.6 has specified drawn circles since M1c and the dive row has drawn them since; the form now uses the same one rather than a second — §4.1's whole point. In the form each dot is additionally its own control and carries its own 48 dp target (§0.5), because there a dot is something you press. SF Symbols through `expo-symbols` with a Material Symbol on Android, exactly as `SearchCapsule`'s magnifier already works.
- **The chevron marks in-place disclosure — on a group header and on a field row alike — and nothing else.** A collapsible group is marked by a chevron, not by the words "Show"/"Hide". **Drawn, not typed** — the same reason §0.6 already gives for rating marks: a glyph's size varies by typeface, so a typed chevron looks broken somewhere. It rotates to show state, needs no translation, and drops a word from a row that is otherwise pure structure.

  **M1h extended the mark to a field row** — the cylinder summary hides its spec fields exactly as a group header hides its rows — and the axis that makes that coherent is worth stating, because the obvious wording is wrong. It is *not* "a field whose value is read rather than typed": that describes `DateTimeField`, which deliberately carries **no** chevron and marks its open state with the `surface` fill instead. The real distinction is **what the gesture does to the page**. A control that **discloses further rows in place** carries the chevron; one that **opens a picker over the row** does not. Two riders follow: the mark is never spent on navigation — a row that takes you somewhere else is not disclosing anything — and the style is named for the rule rather than for its first caller (`disclosureChevron`, not `formGroupChevron`).

Unchanged, and deliberately: the save control stays filled inverted ink (§10), and the Logged/Planned chip and `‹ Cancel` keep the treatments agreed during M1d. This sentence used to end by preserving the `carried ×` chip, **which contradicted the carry-over paragraph three above it** — M1h replaced that chip, that paragraph says so, and this one went on protecting it for two milestones. ## 1. Product & principles

Ponor is a hobby project, published free, for divers who find existing log apps fiddly. It replaces the paper logbook for manual logging: dive count, sites, conditions, gas, gear, and notes. It is not (yet) a dive-computer companion — the schema leaves room for that later. There is deliberately **no trip entity** to create or manage: carry-over prefill covers a trip's shared details, and the dive list groups itself into trips by date and place.

- **Log a dive in under a minute.** Every new dive is prefilled from the previous one. Logging dive #2 and #3 of a trip means changing the depth, the time, and the pressures — nothing else.
- **Only the fields you use.** Everything is optional except the date. Field groups collapse, and any group can be hidden permanently in settings.
- **The map grows itself.** Dive sites and centers are a shared, community-built database. Autocomplete keeps names consistent; fuzzy matching stops duplicates; optional GPS pins put dives on a map.
- **Works at sea.** The whole app runs offline from on-device SQLite. An account is only needed to back up, sync a second device, and contribute named sites — and syncing happens by itself.

## 2. The fast-logging system

The core of the product. Four mechanisms work together.

### 2.1 Carry-over prefill

**Carried over from the last dive:** dive centre and site · entry (shore/boat) · salinity and water body · cylinders (material, configuration, size, working pressure) · gas mixture per cylinder (O₂/He %) · weights · suit and its thickness · equipment (hood, gloves, boots, torch, camera) · buddy and guide.

**Fresh every dive:** max and average depth · duration · time in · starting **and** ending pressure · visibility, both the scale and the distance · temperatures · weather · waves/current/surge · how the weighting felt · rating · title · notes · the exact GPS point (`latitude`/`longitude`).

The three fields M1h added to this half — weather, the visibility scale and the weighting judgement — are fresh for the same reason the pressures are, stated below: they describe the conditions of *one* dive, and a carried-over value that looks like data and is not is the failure this split exists to prevent.

The GPS point is fresh for the same reason the pressures are: the *site* carries, which is the right granularity, but the exact entry position is a claim of precision that a stale value would make falsely. A carried-over pressure or pin looks like data and is not. **The rule is currently unexercised**: M1i took the coordinate rows off the form (§2.2), so nothing writes a pin until M2's map does — the rule is stated here so the map arrives into it rather than deciding it again.

- **Derived automatically:** the dive number (§2.5); the date stays on the previous dive's date when that dive was **today or yesterday** — never when it is dated ahead of today, because a dive that has not happened yet is not recent (§10); used pressure = start − end; surface interval from the previous dive; RMV in l/min when average depth, time, and cylinder size are present.
- **Site defaults:** picking a site prefills entry, salinity, and water body from the site's own defaults — and those win over carry-over when you switch sites.
- **Cylinder presets:** named cylinder sets ("twin 12 steel", "alu 80 nitrox") apply the whole cylinders-and-gas block in one tap. Scoped to the cylinders alone (owner's call, M1e — §10): a suit, weights and hood already carry from the previous dive without being named, and a preset that also carried them would be a second, staler way to fill the same fields.
- **The app learns:** pickers order options by your usage frequency, so your usual cylinder, weights, and suit sit on top without any setup.

### 2.2 Progressive form

One scrollable form. A small core strip is always visible: **date, site and centre** — what identifies the dive rather than what measures it. Everything else lives in seven groups, in this order:

| Group | Holds | |
|---|---|---|
| *Times & depth* | max depth · average depth · duration · time in | **opens by default** |
| *Gas & cylinders* | the cylinder spec · O₂ and He · **start and end pressure** | **opens by default** |
| *Conditions* | weather · water and air temperature · visibility and its distance · waves · current · surge | |
| *Water & entry* | entry · salinity · water body | |
| *Equipment* | suit and thickness · accessories · weights and how they felt | |
| *People* | buddy · guide | |
| *Notes & rating* | title · notes · rating | |

Only the date is required. **There is no "hide fields" setting** — the rule below makes one unnecessary (owner's call, M1i; §10).

**The pressures belong to the cylinder, and the order is what makes that bearable.** They were in the strip, and the owner's reason for wanting them back there is sound — he fills both on every dive. The reason they cannot go is multi-cylinder: a *Start pressure* row in the strip describes `tanks.0` and silently says nothing about the second cylinder, which is a strip lying about what it shows. **So the group moved instead of the fields** — *Gas & cylinders* sits second, above *Conditions*, opens by default, and the pressures are two rows further down the screen than they were, rather than behind a tap (owner's call, M1i).

**Conditions is what the day was like; where you are is a different question.** *Entry*, *salinity* and *water body* sat in *Conditions* and are not conditions — §2.1 gives all three away by prefilling them **from the site's own defaults**. They are properties of the place, they carry over, and they are touched about once a trip, so they get their own group below the one a diver actually fills. Weather leads *Conditions* because it is the first thing anyone notices about a dive day (owner's call, M1i).

**The form has no latitude and longitude rows.** It had two decimal keypads, and nobody has ever typed a coordinate into a phone on a boat — §2.3 has always said the pin comes from the map or *use my location*. The columns stay (§6) and the dive detail still reads a point back when one exists; only the inputs are gone, so **no dive can carry a GPS point until M2's map lands** — which was already true in practice and is now true by design (owner's call, M1i).

**The core strip guessed twice.** It was fixed at date · site · centre · max depth · duration before anyone had logged a dive with it, which left *time in* and the two pressures behind a collapsed group — so surface interval, which the app computes and shows, had its only input hidden, and the diver who fills start/end on every single dive had to open a group on every single dive. Found by the owner using it. The second answer was an eight-field strip holding all of them — which fixed the hiding and flattened structure that was doing work. The third and current answer keeps the strip for identity and lets the groups that earn it start open (§10), so nothing is hidden and a diver who never records an average depth can collapse that group once and keep it collapsed.

**Groups remember themselves, and the memory holds three states, not two.** A group opens when the diver opened it last time **or** when this dive already has a value in it — the second half matters because carry-over fills groups nobody touched. This is §2.1's "the app learns" applied to the form's structure rather than to its values, and it is a display preference: it degrades to these defaults and never blocks a save (§1).

The three states are **never decided**, **opened** and **collapsed**, and the first two sentences of this section only work if the memory can tell the first from the third. M1h stored the *set of open groups*, which cannot: a diver who collapsed *Times & depth* would find it open again on the next dive, because "I closed this" and "I have never touched this" were the same absent row. **"Opens by default" is therefore an answer for the untouched group only** — an explicit collapse outranks it. Found while building M1i, from a brief that asked for a starting state the storage could not express (§10).

**Where the two halves disagree, the value wins**, and the owner's own statement of the rule is the clearest one anybody has managed: *no data = collapsed, data carried = not collapsed*. A remembered collapse cancels the default-open state and nothing more. So a collapse holds for the dive you are logging, and the next dive re-opens whichever groups carry-over has refilled — which is the rule working, not the rule failing.

That was written up once as a defect ("collapsing *Gas & cylinders* can never stick — the chevron is a lie") and it is not one; the note is kept because the reasoning error is instructive. **Four of the seven groups carry** — *Gas & cylinders*, *Water & entry*, *Equipment*, *People* — so a diver on their fifth dive meets five groups open, and that looks like the complaint that started M1h arriving from the other side. It is not the same thing. Those groups are open *because they contain that diver's data*, which is the app showing its work; the M1h complaint was about groups that were **empty and shut**.

**"I never fill this group" needs no separate answer, and this is why v1 has no "Fields I use" screen** (owner's call, M1i, dropping it from scope). A group a diver never fills holds no data, so it never carries, so it stays collapsed — it costs one header row rather than a whole group, and that is cheap enough that a settings screen for it is machinery earning nothing. The four groups that *do* carry are the apparent exception, and **the clear control already answers them**: clearing a carried field writes a real blank (§0.6, §1), so the next dive carries nothing and the group goes quiet. Clearing your buddy once is what "I do not log buddies" means, said in the form rather than in settings, and it is a gesture that already exists.

**The first dive opens everything** (owner's call, M1i). With an empty logbook nothing carries and nothing is remembered, so the value rule would leave a first-time diver with the two default-open groups and five closed ones — the form at its least informative on the one occasion nobody knows what it holds. An empty logbook therefore opens every group, on the same reasoning as the first-run screen teaching §0.1: this is the only time the whole shape is worth seeing, and the condition decays on its own, since it can never be true again.

### 2.3 Autocomplete that builds the database

- Typing a site or center searches **your own history first**, then the on-device copy of the community catalogue — both instant and fully offline. Live search adds anything newer when online.
- Creating a new site asks only for a name; country is inferred, and a GPS pin can be set from the map or "use my location" — pressed right on the boat.
- Before saving a new entry, a fuzzy check suggests near-matches: *"Did you mean Shark Point?"* One tap picks the existing site instead.
- Buddies and guides autocomplete from your own past entries only — they stay private text, not user accounts.

### 2.4 Prepare before, finish after

Logs can be half-written in advance. On the boat, set up the coming dives — date, site, cylinder, starting pressure — and they wait at the top of the list as *Up next*, excluded from stats and dive numbering. After surfacing, *Complete dive* asks only for the missing numbers: duration, depths, ending pressure. A planned dive has no dive number until it's completed.

### 2.5 Dive numbering

**Dive numbers are computed, never stored:** chronological position plus your pre-Ponor dive count (`dives_before`, asked once at onboarding, editable in settings any time). Backfilling an old dive slots it into place and renumbers everything after it automatically — on every device, with zero sync churn. Same-day dives order by time in. When times are missing the diver can order them by hand, which is what `manual_order` stores — a nullable integer used only as a tie-break within one date, and **reordering rewrites the whole day as 1..n** rather than writing a position onto the dragged dive alone (see §10). A dive that has been ordered by hand sorts before one that has not, on the same reasoning as timed-before-untimed; dives with neither fall back to creation order, which is deterministic across devices and is almost always already correct. No per-dive number override in v1 (layer it on later only if real users ask).

## 3. Screens

Four tabs plus a full-screen dive form. Onboarding is two steps — pick units and, for switchers, how many dives you already have; optionally sign in — then straight to "Log your first dive".

- **Dives** — auto-grouped into trips (same dive centre, gaps up to 3 days — §10); planned dives pinned on top as "Up next" **with their date**; search; row = number, site, metadata, and the depth value as the row's anchor (§0.6); hand-ordering behind a day strip; logging a dive is the screen's primary action — a bottom-right "+" while Ponor is tab-less, moving into the top-right capsule when the tab bar lands (see below).
- **Map** — clustered pins of your dives (badge = count per site); tapping a site shows your dives there with a depth/temp summary; toggle to explore all community sites.
- **Stats** — total dives, hours underwater, deepest dive (**`domain/logbookStats.ts` already owns these three**, since the Dives header shows them — M3 renders them, it does not recompute them); countries and sites visited; RMV trend; currency (days since your last dive, refresher nudge after 6 months); charts later, counters first.
- **Settings** — units (m/ft, bar/psi, °C/°F, kg/lb), language; cylinder presets; certification wallet (agency, level, card number); account & sync, data export (CSV + JSON), delete account. ("Fields I use" was listed here until M1i dropped it — §2.2.)
> **Tabs go to the bottom; search and `+` move to a top-right capsule** (owner's call, recorded during M1d, to be built with Settings). Measured on iOS 26, not recalled: Messages (no tab bar) floats a search capsule at the bottom with compose top-right; Photos (tab bar) puts its `[Library | Collections]` capsule bottom-left and search as a detached circle bottom-right. Both are a capsule left, a circle right — exactly the shape Ponor already uses for search and `+` — so the strip holds two objects and we will want three. Calendar answers it: one top-right glass capsule carrying view-toggle, magnifier and `+` as equal monochrome glyphs, with the bottom left to navigation. Ponor follows that. Rejected: keeping `+` bottom-right and hiding search behind a pull-down — more code, and a hidden affordance, which is the same complaint that already cost the reorder control a redesign. **Built with `expo-router`'s native tabs** (`unstable-native-tabs`), so iOS 26 draws its own Liquid Glass bar with the platform's scroll-edge behaviour and accessibility rather than an approximation of them — the owner's call, and the reason the bar looks right without us styling it. **The browser runs a different navigator on purpose:** expo-router's web implementation of native tabs is a *top-centre text pill* with no icons, fixed by its own CSS at `top: 24px`, which both contradicts this decision and collided with the capsule at narrow widths. Web therefore uses the ordinary JS `Tabs` through a `_layout.web.tsx`, styled to this spec. Fighting the native-tabs web CSS with selectors on its internal markup was rejected: it is an `unstable_` API and that breaks silently on upgrade.
>
> The cost is real and accepted: the `+` leaves the thumb zone §0.5 reserves for the primary action, and stops being big. It is not abandoned — **the empty logbook is a first-run screen (§0.6) and keeps a full-size "Log your first dive" at the bottom of it**, so the diver who most needs reach keeps it, and the top-right capsule serves the returning diver with a populated list. Whether `+` is an equal glyph or carries some emphasis is decided when it is built; §10's "no accent on the `+`" binds either way, since that was about hue, not weight.

### 4.1 One owner per rule

This project's defining defect is one rule written in two places, then drifting. It has produced dive numbers reading #2, #1, #3; a date contract asserted three ways at three strictnesses and enforced in none; a site name that said "Unnamed site" in the list and nothing at all on the detail; a cylinder material rendered "Steel" on one screen and "steel" on the next; and, twice, a *Complete dive* button wired to the plain edit route, completing nothing while saying it did. Every one shipped green.

**Each of these owns its class of rule. A second implementation is a defect, not a style preference:**

| Owner | Owns |
|---|---|
| `domain/types.ts` | Every closed vocabulary a form offers as a fixed list — the list is the source and the type is derived from it, never written twice — and **how many cylinders a rig is** (`single` 1, `twinset` 2, `sidemount` 2), which `derived.ts` calls rather than re-deriving. |
| `domain/datetime.ts` | Every reading of a `YYYY-MM-DD` or `HH:MM` string, and every conversion to or from a `Date`. Never `toISOString()` (UTC) and never `new Date('2026-08-31')` (UTC midnight) outside it — three separate bugs came from exactly those. |
| `format/display.ts` | Every conversion of a stored value into diver-facing text. |
| `format/units.ts` | The unit system, the four pairs, their conversion factors and their per-pair precision. |
| `theme/styles.ts` | Every place a token meets a style property. `theme/depth.ts` is the only reader of the depth scale; `theme/resolve.ts` the only reader of the token sets. |
| `domain/diveNumber.ts` | Dive ordering and numbering (§2.5). |
| `domain/trips.ts` | Trip grouping (§3). |
| `db/dives.ts` | Every write to a dive, and the `undefined` = don't touch / `null` = clear patch contract. |
| `db/gearPresets.ts` | Every write to a preset, under the same contract — including that a write changing nothing must not advance `updated_at`, which §7's last-write-wins is keyed on. |
| `db/liveQuery.ts` | Two adjacent facts about a live read, and both are about *time*, not content: whether it has produced an answer yet (`resolved` — because "still looking" and "nothing there" are what an empty array cannot tell apart), and whether a failure is still what the read last said (because `useLiveQuery` sets `error` in its failure paths and **never clears it**, so a notice keyed on it outlives the failure it reports). |
| `db/tombstone.ts` | `liveRows(table)` — the tombstone filter every read of every soft-deleted table applies. Was `liveDives` alone until a second such table existed (M1e). |
| `supabase/migrations/` | The Postgres shape of every synced table — columns, types, defaults, indexes and RLS. |
| `src/db/schemaParity.test.ts` | The tie between that and `src/db/schema.ts`. §6 has claimed "the same schema lives in SQLite and Postgres" since M0 and nothing checked it; a column added to one and not the other is a row that syncs to nowhere and fails no gate. Legitimate differences are an explicit exception list, so each one costs a deliberate edit. |
| `domain/logbookStats.ts` | What a logbook adds up to — total dives, hours underwater, deepest dive, in SI and unformatted. | `db/settings.ts` | What a settings row *means* — every coercion of a stored string back into a value, and every default a missing or nonsense row falls back to. | `domain/presets.ts` | Preset ordering, preset name identity, and **what refuses a preset save** — the three sentences and the verdict behind them, shared by the dive form's capture and §3's editor. | `domain/suggest.ts` | What autocomplete offers for a field and in what order (§2.3). |
| `domain/search.ts` | `foldForMatching` — how text is read before it is compared, on **both** sides and for both features. §10 puts diacritic folding in M2 for search and autocomplete alike, so written twice that change lands in one place and leaves the other behind. |
| `navigation/leaveScreen.ts` | Where leaving a screen lands, and the guard that a diver who deep-linked into it still reaches somewhere real. Two destinations exist now — the dive list and Settings — so the rule is shared rather than per-screen. |
| `cloud/supabase.ts` | Whether there is a backend at all, and the client when there is one. Reads the two `EXPO_PUBLIC_*` variables as literal member expressions — see §10, that is load-bearing, not style — and treats absent, blank and whitespace alike as *no backend configured*. |
| `cloud/sessionStore.ts` | Where an auth session is kept: the keychain on a device (`expo-secure-store`, §4), `localStorage` in a browser, which is **not** a keychain and is acceptable only under §9's testing-target rule. |
| `src/testing/` | Shared test guards, so a guard cannot be broken in one copy and sound in four others. |
| `src/platform/` | Behaviour that genuinely differs by platform, so a screen never branches on platform itself. |
| `components/symbolName.ts` | The per-platform key an SF/Material symbol is requested by — **owner enforced and every caller witnessed** (M1h), all sixteen call sites asserting the Android and web names, not only the iOS one that a simulator would have shown. The two tab layouts are handed **pre-resolved** icons by `navigation/tabs.ts`, so passing an unresolved symbol there does not compile — which is how a rule reaches `src/app/`, a tree that carries no tests by design. |

**Three rules keep it that way.**

*Derive, or tie at compile time.* A list that can be computed from another is computed — `FRESH_FIELDS` is the schema's keys minus `CARRIED_FIELDS`, not a second list. One that cannot be gets a type-level assertion that fails the build when the two diverge; `TankFormFieldsMatchTank` and `StatusFormValuesMatchDive` in `diveFormSchema.ts` are the pattern to copy. Adding a member to a hand-maintained option list used to produce a save-blocking rejection and a missing chip, silently.

*One deliberate exception, until i18next.* Roughly twenty-five field labels are duplicated as literals across the form and the dive detail — "Water temp", "Max depth", and so on. They agree today, and each is one edit from becoming the `O2 %` / `O₂` drift again. They are **not** unified yet on purpose: translation has to key every one of them, and that pass is where the set belongs. Doing it twice would be waste; leaving it unrecorded would make it look like an oversight.

*A deliberate near-duplicate names its siblings.* Some rules look alike and answer different questions, and unifying them is itself a bug. Three read a dive's place: `tripKeyOf` groups (centre first, **may be null**, so "no place recorded" stays distinguishable from a dive actually named "Unnamed site"), `diveSiteLabel` displays (site first, **never null**, because a row with no heading is a blank line), and `ReorderControls`'s `rowLabel` speaks (**omits** the placeholder, because position already identifies the row and "Unnamed site" would be noise in speech). Each carries a note naming the others and the question each answers. Without that note, the next reader sees three copies of one rule and helpfully unifies them.

## 5. Backend on Supabase

One Supabase project (EU region, Frankfurt) provides everything server-side; we write SQL and policies, no server code and no hosting. Row-Level Security is the security model: dives are readable and writable only by their owner; sites and centers are readable by **every signed-in user**.

**"Readable by everyone" was ambiguous and M2a had to pick.** It can mean every *user* or every *caller* — and the second makes the whole catalogue public to anyone holding the publishable key, which ships inside the app. The schema revokes `anon` on all six tables, on the reasoning that opening this later is two documented statements and closing it after a scrape is impossible. Revisit when the community catalogue is worth showing off; the app itself never needs it, since §2.3's autocomplete runs off the on-device copy.

- **Auth:** email and password first; Sign in with Apple and Google before release. Apple is mandatory once Google is offered (App Store rule 4.8).
  **The email method was a one-time code, then a magic link, and is now a password** (owner's call, M2). Codes read better on mobile and were chosen for that; delivering one needs an email template edit, **template edits need custom SMTP, and custom SMTP needs Pro** ($25/mo, which §8 puts thousands of users away). The fallback was the default magic link — free, one redirect entry — and the owner rejected it on taste, which is a legitimate reason for the one screen every diver meets. **Email and password needs no email at all**: sign-up with confirmation disabled sends nothing, so it clears the same wall from the other side.
  **Password reset works, and the paragraph that said it did not was wrong.** The wall is on *editing* a template, not on *sending* one: Supabase ships default `Confirm signup` and `Reset password` templates and the built-in mailer sends them on the free tier. Recovery therefore needs a `ponor://` redirect entry and deep-link handling, and nothing else. **Recovery is a link and login is not**, which is the distinction that makes this sit alongside the owner's objection rather than against it — a link is a bad thing to meet every time you open an app and a fine thing to meet once, on the day you have forgotten something.

  **Sign-up confirmation is on, and its job is not recovery** (owner's call). Recovery already reaches any address on file, confirmed or not. What confirmation catches is the **address that was never yours** — a typo at registration is the one case where recovery genuinely cannot work, because the reset mail goes somewhere real and unreachable. Note the consequence, since it removes a design the owner had sketched: Supabase's confirmation **gates the first sign-in**, so there is no interval in which an unconfirmed diver is using the app and could be shown a banner. One email, at registration, once.

  **The free tier's real email limit is volume, not capability** — the built-in mailer allows a few messages an hour, project-wide. Irrelevant at one diver, and a reason to expect §8's Pro line sooner than the database will force it. **Apple and Google remain wanted before release** (§5's list, App Store rule 4.8) and neither needs Pro: Google is a free Cloud project, Apple comes with the developer account required to ship at all.
- **PostGIS** stores site coordinates and answers "sites near me"; **pg_trgm** powers fuzzy autocomplete and duplicate detection — the map and the dedupe are features of the database, not app code.
- **Community model:** any signed-in user can add a site or center; rows are never hard-deleted. Bad entries are fixed by an admin setting `status` to `merged` with `merged_into` pointing at the survivor. Dives store a name snapshot, so history never breaks.
- **One canonical record per site:** the creator and the admin edit its facts (pin, entry, salinity, site depth); everyone else taps *"suggest a correction"*, which lands in a review queue — **`site_edits`, read by its own author and by the admin in Studio, and not by the site's creator** (M2c). A suggestion is free text from an identified diver, and routing that to another diver is a moderation surface §9 defers as a class; the creator's editing rights are over the site's facts, not over other people's messages. Opening it to the creator later is one policy.
- **Deleting an account leaves its sites standing, and nobody can edit them again** (M2c, and this is the sentence §5 was missing). §8 requires in-app deletion; the rule above requires community rows to survive, since other divers' dives point at them. So a departed diver's dives, presets, certifications and profile cascade away and their sites, centres and suggestions stay with `created_by` set null. **A null matches no `auth.uid()`, so those sites become editable by nobody through the app — including the same person signing up again.** That is coherent: they have become community records, corrected through `suggest_site_edit` like anyone else's. It is also permanent, and worth stating before someone reads it as a bug. Divers who disagree with a pin still get precision — a dive can carry its own optional GPS point, and the personal map prefers it.
- **Offline dedupe:** the compact site/center catalogue syncs to every device (all of it while the community is young, country-scoped once it isn't), so autocomplete works fully offline. When a site created offline is pushed, the server reruns the fuzzy check and flags likely duplicates for a one-tap merge by the creator — admin merge is the backstop.
- **Seeding, later:** the catalogue is community-grown first. Open data can top it up one day — Wikidata is CC0 and safe to mix; OpenStreetMap has good dive-center coverage, but its ODbL share-alike would commit the catalogue to an open license. A deliberate decision for later.
- **RPC functions** (Postgres, callable from the client): `search_sites`, `similar_sites`, `suggest_site_edit`, `pull_changes`, `push_changes`, `delete_account`. No Edge Functions needed for v1.
  **Two gaps this list has, found while building it** (M2c): §2.3 promises live search for **centres** as well as sites and there is no `search_centers` here, so a centre typed online today is answered only from the device's own copy; and §10's diacritic folding — the rule that lets *Šárka* be found by typing *Sarka* — has **no server half**, because `unaccent` is not installed. Both are additive and neither blocks M2's sync; they belong to whichever task first makes online search real.

**Free-tier caveat:** free projects pause after 7 idle days. A weekly GitHub Action pinging a health endpoint keeps it warm during quiet months; once there are real users, the problem disappears — and the app works offline regardless.

**Admin in v1 is Supabase Studio.** The merge and suggestion queues are just tables to review there, and usage stats (users, dives per week, new sites) are SQL views. A real `/admin` area arrives with the web app and reuses its codebase.

## 6. Data model

The same schema lives in SQLite (Drizzle) and Postgres. Conventions: **SI units stored**, converted at display · IDs are **client-generated UUIDv7**, so offline creation never needs re-mapping · every column nullable except `id`, `user_id`, `date` · all synced tables carry `created_at`, `updated_at` and `deleted_at` (tombstone). `created_at` is not bookkeeping: dive numbering uses it as an ordering tier for same-day dives with neither a time nor a hand-set order (§2.5), so it must be preserved across sync rather than regenerated.

**On `updated_at`:** the client stamps it locally on every write, and §7's `push_changes` restamps it with the server clock from M2 onwards. Until M2 exists there is no server to set it, so an M1 reader should not go hunting for server code — the repository is the only writer. It is load-bearing either way: §7's whole-row last-write-wins is keyed on this column, so a write that changes nothing must not advance it, or the device that did nothing wins the conflict against the device that did something.

**On `tanks` being non-nullable** (the one exception to "everything nullable"): an empty array already means "no cylinders recorded", so a nullable column would add a second way to say the same thing and force every reader to handle both. The column is NOT NULL with a `'[]'` default and the domain type is `Tank[]`, not `Tank[] | null`.

### `dives` — private, one row per dive

| Cluster | Fields |
|---|---|
| Identity | `status` (logged·planned) · `date` · `time_in` · `manual_order` · `duration_min` · `title` · `notes` · `rating` (1–5) |
| Where | `site_id` + `site_name` snapshot · `center_id` + `center_name` snapshot · `entry` (shore·boat·other) · `salinity` (salt·fresh) · `water_body` (ocean·lake·river·quarry·cave·pool) · `latitude` + `longitude` (optional exact GPS point) |
| Profile & conditions | `max_depth_m` · `avg_depth_m` · `water_temp_c` · `air_temp_c` · `visibility` (high·average·low) + `visibility_m` · `waves` (0–3) · `current` (0–3) · `surge` (0–3) · `weather` (sunny·partly·cloudy·rainy·windy·foggy) |
| Gas & cylinders | `tanks` — JSON array, one entry per cylinder, first = main: `{ material (steel·alu), configuration (single·twinset·sidemount), sizeL, workingBar, o2Pct (21 = air), hePct, startBar, endBar }`. **Nitrogen is never stored** — it is 100 − O₂ − He and is drawn as a computed value (§0.6). |
| Equipment & people | `suit` (none·shorty·wet·semidry·dry) · `suit_thickness_mm` · `equipment` — token set (hood·gloves·boots·torch·camera) · `weights_kg` + `weights_feel` (under·good·over) · `buddy` · `guide` |

**What a column becomes in Postgres** (M2a, because "the same schema lives in both" did not say). **Calendar dates and clock times are `text`, not `date`/`time`** — `storedCalendarDate` deliberately stores an uninterpretable date unchanged (§1 never blocks a save), and §7 pushes in one transaction, so a `date` column would freeze a diver's entire sync over one bad row. **Timestamps are `timestamptz`**, which §7's ordering depends on. **No vocabulary column is an enum and none carries a CHECK** — §10 already rules that a value from a client this build does not know is stored and flagged rather than rejected, and an enum makes that impossible without a migration; this is that ruling arriving in the section a schema author actually reads.

**On the GPS point:** SQLite has no point type, so a dive's optional exact position is two nullable columns on the device. Postgres composes them into a PostGIS point — the sync payload carries the pair, and the server owns the geometry. **Not built in M2a and deliberately so:** nothing in v1 reads that geometry, and a generated column wrapping PostGIS is the single statement most likely to fail on a server nobody here can test against. The `alter table` is written down in `supabase/README.md`. If it is still undone when M2 closes it belongs on §9's shelf rather than sitting in this paragraph reading as done. `dive_sites` keeps a single PostGIS `location` because that table is server-authoritative.

**The keys inside `tanks` are camelCase, unlike every column name.** That is deliberate. Column names get a mapping layer — camelCase in TypeScript, snake_case in SQL — but a JSON blob's interior gets none: whatever the app writes is what is stored, and changing it later means rewriting every row *and* re-agreeing with Postgres `jsonb` in M2. camelCase is the lower-friction end, since the app reads these keys directly.

Tanks are one JSON column instead of a child table: they are never queried on their own, and whole-row sync stays trivial. The form shows a single cylinder until "+ add cylinder" is tapped — multi-gas ready without multi-gas clutter.

**Computed in the app, never stored:** the dive number (chronology + `dives_before` offset), used pressure, RMV across all tanks, MOD when diving nitrox, time out, surface interval.

  **Two corrections this line carried until M2d.** It said *hidden groups*, which was "Fields I use" — dropped in M1i, and §2.2's collapse rule is what replaced it. And it put the **dirty flags inside `sync_state`**, which contradicts §7's own wording: a flag is **per row**, a column on each synced table, because "which rows are owed" is a fact about rows and a single state row cannot hold it. `sync_state` holds one timestamp and nothing else.

Without them `pull_changes` returns a catalogue with nowhere to put it and §2.3's *"the on-device copy… fully offline"* is a promise nothing keeps. **They have two writers with different rules and therefore different types**: a site created on a boat is dirty and will be pushed; a row arriving from a pull is not, and the function that applies it takes a type with nowhere to say otherwise.

## 7. Sync protocol

A deliberately small, WatermelonDB-style delta sync — two RPCs, whole-row overwrite. Safe here because every private row has exactly one author; conflicts only occur between one person's own devices.

**The server's rule is last *push* wins, not last *write*, and the difference is worth stating** (M2g, where this paragraph said "last-write-wins" and the SQL never compared anything). `push_changes` upserts with no `where` clause and stamps `updated_at` with the moment the row arrived, so a phone that has been offline for a week goes up carrying older content and overwrites what the server holds. **Kept deliberately.** Genuine last-write-wins would mean comparing a timestamp the *phone* wrote, and §7.3 exists precisely because phone clocks cannot be trusted — a device an hour fast would win every conflict for as long as it stayed wrong. And the loser here is always the *other* device's edit, never the pushing device's own, which is the direction that matters: the diver doing the pushing is the one looking at the screen. Changing it costs a comparison in six upserts **and** a client-side answer for a row the server declined, which is a design question rather than a clause.

1. **Push.** Rows flagged dirty go up in one transactional `push_changes` call — dives, presets, and any sites or centers created offline. RLS validates ownership; the server stamps `updated_at` and returns canonical rows; the client clears its flags.
2. **Pull.** `pull_changes(last_pulled_at)` returns the user's changed rows plus the compact community catalogue — all of it while the community is small, country-scoped later. The client upserts by comparing `updated_at`, **and only over a row it does not still owe the server** (M2g). That second condition is not a refinement, it is what stops one device losing an edit to itself: push restamps `updated_at` with the server's clock, so the server's echo of a row can outrank an edit made on the phone *after* the push went out, purely because phones run behind. Under a timestamp alone the echo wins and takes the dirty flag with it — the very flag that would have sent the edit. A dirty row is therefore left alone until it has gone up, and the server settles it on the next push. **The consequence, stated rather than left emergent: a row that cannot be pushed stops receiving server updates entirely, for as long as that lasts.**

   **A tombstone is applied, not deleted.** This step used to read "tombstoned rows are removed locally", which is not what the client does or should do: the tombstone is *written* to the local row and `liveRows` (§4.1) hides it from every read. Deleting it would throw away the fact of the deletion, which is the one thing a tombstone exists to carry.
   **The comparison is a string comparison, so the RPCs must return timestamps in the client's own `toISOString()` spelling** (M2a). Postgres will happily hand back `2026-09-02 09:00:00+00`, which sorts differently from `2026-09-02T09:00:00.000Z` — and the failure is not an error, it is **the wrong device winning a conflict**, silently, on rows nobody is watching.
   **The watermark a pull returns is deliberately behind the clock** (M2b). `now()` in Postgres is transaction start, so a push committing after the pull took its snapshot carries an earlier stamp than the watermark — and would be skipped **on every future pull, permanently**. The response therefore returns `now() - 1 minute`, so the next pull re-reads a small overlap; re-reading is free because the upsert is idempotent. There is no exact answer computable from inside the function, and a lost row here is silent.
3. **Server clock only.** `last_pulled_at` comes from the server's response, never the phone's clock — divers change time zones constantly.
4. **Guest → account.** On first sign-in, every local row is marked dirty and pushed; the server writes the owner. That is the entire "optional account" migration — the payoff of client-side UUIDs. **This used to read "local rows get the new `user_id`", which described a column that does not exist** (M2b): the device has no `user_id` anywhere, because a device holds exactly one person's logbook and a column repeating the same value on every row would be storage pretending to be a key. Nothing on the client changes at sign-in but the dirty flags.

   **Signing out wipes the local logbook** (owner's call, M2b). The data is on the server, signing back in re-syncs it, and a device that keeps one person's dives after they have left is the only way a second account could ever see them. So sign-out is a real erase, and the app must say so before it happens — it is the one destructive action in v1.

   **The wipe restores the device to its guest state: everything that came from an account goes, everything the diver set on this device stays.** `dives` and `gear_presets` go. `sync_state` goes, and that one is not optional — a stale `last_pulled_at` makes the next account's first pull skip every row older than it, silently and with no repair. The catalogue tables go too, which is the least obvious of the four: they arrive by pull, so a guest never had them, and keeping them would leave a site created offline sitting in the next account's dirty set to be pushed as **their** creation. `settings` **stays** — units, locale and the form-group memory are things this diver set on this device and re-asking would be hostile — with `dives_before` the one exception, because §6 syncs it to the profile and leaving it would hand the next account a wrong pre-Ponor number that shifts every dive number after it.

   **Sign-out pushes first, and refuses if anything is still dirty** (M2g, discharging M2e's build-order constraint by replacing it with the rule it was standing in for). The confirmation promises the logbook comes back, which is true only of rows the server has. So the wipe attempts a push and then **counts what is still owed** — and it counts the rows themselves rather than believing the push's own report, because a push that returns success while storing nothing is exactly the failure this guard exists for. Nothing is deleted before that count is taken. This covers what the ordering constraint never could: the diver who has been offline a month, the push that half-succeeded, the build with no backend at all.

   **Local dives are always adopted, even by an account that already has dives** (M2b). The case is a diver who logs a few offline and then signs into an existing logbook, and the question is only interesting because the phone might have been someone else's. Adopting is right anyway, on an asymmetry: adopting wrongly puts a handful of visible, deletable dives in the wrong logbook, and discarding wrongly destroys dives that exist nowhere else. **UUIDs mean there is nothing to reconcile** — the local rows push as new rows, the account's rows arrive in the pull, and nothing collides. The app **states what it did** afterwards rather than asking first: a prompt at sign-in is a wall in front of the one flow §1 promises is optional, and the answer it collects is one the diver can give better by looking at the list.
5. **Triggers.** **A session arriving**, app foreground, a debounced 10 s after any save, and pull-to-refresh — with a retry ladder standing in for "connectivity restored".

   **A session arriving is the trigger this list was missing** (M2h), and without it the other four do not close the case §7.4 opens: `AppState` is already `active` at launch, so there is no foreground *transition* to fire on, and a diver who signs back in after the sign-out erase would sit looking at an empty logbook whose rows are safe on the server and which nothing on the device would ever ask for. It is keyed on the **user id** rather than on the session object, because a token refresh hands over a fresh session every hour.

   **"Connectivity restored" is not observed.** `@react-native-community/netinfo` is a native dependency and a rebuild; instead a failed cycle retries on a doubling delay from 30 s to a five-minute ceiling. That covers the case that matters — the phone regains signal while the diver is looking at their list and saving nothing — without claiming to know anything about the radio. It is later than netinfo would be, and it cannot tell a lost signal from a server refusing this device.

   **The save window does not restart.** A trailing-edge debounce is pushed forward by every save inside it, so a diver saving every eight seconds would never sync at all. The first save arms the window and every save inside it rides that cycle: eight edits, one sync, never more than ten seconds behind the first of them.

   **One cycle at a time, never while signed out, never on a build with no backend.** Two overlapping cycles are not two syncs — both push the same rows and each clears flags against a clock the other has had restamped, so a flag gets cleared for a row the server took a different version of. The refusals live in the engine rather than at the trigger sites, and the session is re-read at the moment a cycle runs: a save window is ten seconds long and signing out is one tap. **The wipe takes the same lock**, because triggers created a window in which a cycle lands between the erase and the sign-out and pulls the logbook back onto a device that is leaving the account.

   **A quiet indicator shows pending changes; sync failures never block logging.** It is the Dives header's third line — `3 changes waiting to sync`, in the summary's own muted mono — and it appears **only when signed in**, because every write flags a row whether or not there is an account and a guest would otherwise read "128 changes waiting to sync" with nowhere to send them. It is not a fourth segment on the summary line: those three figures describe one population, and this describes the device's obligation. **An automatic failure says nothing** — the line simply stays, which is the true report — and only pull-to-refresh, which a diver asked for, is answered in words.

**Web is pulled forward out of v1.1** (owner's call, during M1d) — but as a **testing target, not a supported platform**: no store listing, no parity promise, and no obligation on later features to work there. The reason it moves is not only that a browser is a faster way to actually use the app than a device build; it is that the blocker lives in the **data layer**, which M2's sync will be built on top of. Finding out at v1.1 that synchronous SQLite-over-a-worker cannot work on web would be expensive; finding out now is cheap. **It works.** A browser build logs, edits and lists real dives out of wa-sqlite in OPFS, and survives a page reload — verified in Chrome, not inferred. The full account is `.superpowers/sdd/web-spike-report.md`; what the data layer learned, and what M2's sync inherits from it:

- **`openDatabaseSync` cannot be the browser's entry point, and no timeout makes it one.** The earlier diagnosis here — a race between a spin-loop budget counted in iterations and a worker still compiling 621 KB of wasm — was wrong about the mechanism and right only about the remedy. A dedicated worker's script is fetched and started *by its parent's event loop*, so the spin loop blocks the very thread that would boot the worker it is waiting for: measured, the main thread span 134 million iterations over 20 seconds and the worker never answered. The main thread has to yield once. `src/db/client.web.ts` opens the database with `openDatabaseAsync` and gates the app on it; every synchronous call after that works, in ~12 ms.
- **Every synchronous result of 256 bytes or more came back truncated** — `patches/expo-sqlite+57.0.2.patch`, an upstream one-line bug in the bridge's length header. This is the finding worth having early: the sync bridge was not slow, it was *wrong*, and saving any dive at all failed on it.
- **A synchronous result over 1 MiB never returns at all. A second, unrelated ceiling sits underneath it: wa-sqlite's OPFS access-handle pool is **six files**, and it only grows through an `addCapacity()` call `expo-sqlite` never makes — so an origin that has accumulated stray databases simply cannot create another, and the app reports `cannot create file`. Deleting individual pool files makes it *worse*, since capacity is the file count. Ponor gets roughly five spare slots, shared with anything else on the same origin. M2 must know this before it considers a second database.** The bridge's result buffer is 1 MiB, the worker throws while writing past it, and the lock is never released — the app sees "Sync operation timeout", which is not what happened. At ~600 bytes a dive that is a ceiling around 1,700 dives in one `SELECT`, and M2's pull batches must stay under it or page.

Four native-only gaps in the browser, none of them the data layer, and three now closed. `@react-native-community/datetimepicker` ships no web build — `DateTimeField.web.tsx` uses the browser's own inputs, which keep §10's "an invalid date cannot be entered" for free. `Alert.alert` is an empty function in `react-native-web`, so *Delete dive* opened no dialog: `platform/confirmDestructive.ts` now owns the confirmation, native keeping the platform `Alert` unchanged and web using `window.confirm` — which honours §10's actual rule, that the destructive weight belongs to chrome **the app does not draw**, rather than working around it. `expo-font`'s config plugin is native-only, so the browser drew everything in its default serif; `theme/loadFonts.web.ts` loads the same six faces, and `app.config.ts`'s `.ttf` list is now derived from `tokens.js`'s font map instead of being a second copy of it. `expo-symbols` reads a `web` key the app never supplied, so the search and entry icons were absent; `components/symbolName.ts` derives it for both call sites. Still open: `react-native-maps` has no web support, so M2's Map tab will not render there.

A set drawn for this app — the chip scales, and whatever else earns one — is a design job rather than a mark-per-row patch, and `Entry`'s shore and boat are the standard it has to beat.

**A "Fields I use" screen**, if anyone ever asks for it (dropped from v1 in M1i). It would hide whole groups from the form. The reason it is here rather than in §3 is that the group memory plus the clear control appear to cover it entirely — an unfilled group carries nothing and stays collapsed, and a carried field can be cleared into that same state. **The signal that would bring it back is specific**: a diver who says a group will not stay shut *and* who has already tried clearing the field that keeps it open. Anything less is the setting being built for a problem the rule already solved.

**Owed from M1h, and it is a design decision rather than a gap:** carry-over marks and clears every field it fills except **equipment**. That row is five Yes/No controls with no per-value trailing edge to hang a mark or a ring on, so every dive after the first inherits five accessories carrying no mark at all — under a header that says *"clear any of them"*. Naming it in a code comment is not enough, and inventing somewhere to put the mark is a decision about what that row *is*, not a fix. It waits for whoever next looks at the equipment row — which §10 already defers separately, since M1h split suit, thickness and accessories and left the accessories' own shape for later.

**After release — v1.1 and beyond, roughly in order:** the admin area · photos (compressed on-device, per-user caps) · dive-computer & app import (UDDF / Subsurface / Garmin FIT, a PADI migration, plus UDDF export) · site pages with community aggregates · social last, deliberately: linked buddies and site comments bring App Store moderation duties (reporting, blocking), so they wait until the app has earned them.

**Migrating from the PADI app:** PADI's web logbook talks to a GraphQL API, and community tooling already exports it as JSON/CSV (see [PADI-Logbook-exporter](https://github.com/karnovnik/PADI-Logbook-exporter)) — summary fields only, since PADI stores no depth profiles and rarely a start time. Our importer maps that JSON; a GDPR portability request is the fallback. Real depth profiles come from dive-computer files (UDDF, Subsurface, FIT) and draw the profile chart on the dive detail.

## 10. Decision log

Key decisions and the alternatives they beat — don't relitigate without new information.

- **Supabase over a custom .NET API** (v1): $0 and no ops; plain Postgres underneath, so migrating to self-hosted .NET + Postgres later needs no redesign.
- **No trip entity:** carry-over prefill + auto-grouped list instead; a nullable `trip_id` can be retrofitted (even backfilled by date clustering) if users ask.
- **Tanks as a JSON array on the dive row,** not a child table: never queried independently; keeps sync whole-row.
- **Dive number computed** (chronology + `dives_before` offset), never stored: backfill renumbers for free; no per-dive override until real users ask.
- **Starting pressure is not prefilled** from the previous dive (explicit owner decision).
- **Offline-first with whole-row LWW sync:** acceptable because each private row has a single author.
- **Sign-in optional;** guest → account is just claiming rows (client UUIDs).
- **Email OTP over magic links;** EU region (Frankfurt); SI units stored, converted at display.
- **Photos, web, imports, social deferred** past v1 in that order; social last because UGC brings App Store moderation duties.
- **Named Ponor** (§0): the same word in Czech and English, pronounced identically, and free where it counts — `ponor.app` registered. Beat Slate, Bezel, Sextant, Halocline, Atoll, Manta and Deco, each of which failed an App Store or trademark check.
- **Colour encodes depth and nothing else;** controls stay monochrome. The scale follows the order in which water removes colour, so it carries meaning rather than decoration, and depth is always shown redundantly as a number.
- **Dark and light both ship from M0,** not M3: the token set has to exist before the first screen does, and retro-fitting a theme onto built screens is the expensive path.
- **No styling framework — `StyleSheet` built from the tokens** (revised in M0, replacing NativeWind in §4). NativeWind v5 is the only line supporting React Native 0.86 and it is a preview that does not work: Tailwind's `@theme` needs a PostCSS setup Expo does not run by default, and once wired up `react-native-css` fails to deserialize its own compiled output — the same error breaks Expo's own bundled `@expo/log-box` stylesheet. Verified on a simulator, not inferred. A `makeStyles(scheme)` helper over `tokens.js` costs little and keeps the single-source-of-truth property; revisit when NativeWind v5 is stable.
- **`tanks` JSON keys are camelCase** while every column is snake_case: a JSON interior has no mapping layer, so the casing the app writes is permanent, and changing it after users have rows means rewriting every blob and re-agreeing with Postgres in M2.
- **No CHECK constraints on `rating` or the 0–3 condition scales:** §1's "never block a save" argues against hard database rejections, and a CHECK would also reject a row synced from a future client with a widened range. SQLite CHECKs need a table rebuild to add, so this is recorded rather than left to be re-derived. **The same decision covers the TypeScript types**, which stay `number | null` rather than literal unions (`1|2|3|4|5`, `0|1|2|3`): an M2 sync delivering `rating: 6` from a future client is a runtime reality, and typing it as impossible would make the repository's row-to-domain cast a lie. Narrowing them would also break the schema↔domain drift assertion in `db/dives.ts`, since Drizzle's `integer()` infers `number | null` and cannot be narrowed from the schema side. Range handling belongs at the form boundary — but as a **warning or a correction, never a rejection**: §1's "never block a save" binds the form as hard as it binds the database, and a diver on a boat does not get to argue with a validator. A value outside the expected range is saved and can be flagged; it is not refused. **Half discharged at the end of M1d:** the fixed-option and boolean fields now keep and flag a value they do not recognise rather than refusing the save, which is what a dive synced from a newer client will deliver. **Discharged in M1h, and the delay paid for itself.** The four scales became chip rows, which is what made the gap *visible*: a stored `rating: 9` matches no chip, so the row would have read as **unset** — the value surviving in the database while the screen denied it. As text fields they had simply shown the 9, which is why nothing had forced the question. **The flag is a sibling of `UNKNOWN_OPTION_NOTE`, not the same sentence**, and the difference is who could have produced the value: every other flagged field can only receive a strange value from a newer client, so blaming one is fair. These four are the only fields in the app where **the diver could have typed it himself**, and telling him it came from a future version of Ponor would be false. So the note names the number, promises it is kept, and attributes it to nobody — *"9 is not one of these options. It is saved as it is — tap an option to replace it."* **What the note must be is stated here; how it is defended is a separate question, and the first attempt got it exactly backwards.** The intent was a test asserting the *absence* of attribution, so that rewording stayed free and re-blaming did not. What shipped banned two substrings and pinned one literal — so a differently-worded blame passed and an innocent rewording failed, the opposite of the rule in both directions. Recorded because the entry asserted the property as built before it was, which is the same drift this entry's own "Still owed" half was written about. **The property is held by review, not by the suite, and that is the settled answer rather than a deferral.** The second attempt bans a *grammar* of origin — past-tense authorship plus `from`/`by`, proved to have teeth by rejecting `UNKNOWN_OPTION_NOTE` itself — and a review defeated it in one line: *"9 belongs to another version of Ponor, not to you…"* is present-tense attribution using none of the banned words. **No predicate over the string can hold this**; every syntactic approximation has a counterexample shorter than itself, and the failure mode is a check that reads finished. The only genuinely enforceable shape is to stop writing the note as free prose and compose it from a closed clause set — rejected as more machinery than one sentence deserves, and because it collides with i18next: Czech clause order and agreement do not decompose the way English does, so the vocabulary that made it checkable in English would stop being one in translation. The defeat sentence is written into the test's own docblock so it is not re-found later as a bug, and that docblock now states what it catches and what it cannot. Recorded also because this entry described the flagging as built for the length of M1d and it never was — found by a review reading the plan against the code in both directions, which is the only way that drift surfaces.
- **Empty numeric form fields must reach the domain as `null` or `NaN`, never `0`.** `Number('')` is `0`, and `derived.ts` classifies `0` as *contradictory* for `sizeL`/`count`, which voids the whole dive's gas figure rather than skipping one cylinder. A bare `z.coerce.number()` calls `Number()` internally, so it silently blanks a dive's RMV the moment a cylinder field is left empty — no rejected form, no flagged field, just a quietly missing gas figure. Every Zod schema for these fields maps an empty string to `null` instead. This binds the first file M1d writes, long before anyone has reason to open `derived.ts`; the full reasoning lives in the `COERCION CONTRACT` block there.
- **One owner for the `YYYY-MM-DD` / `HH:MM` string forms** (`domain/datetime.ts`, added in M1a): the contract was previously asserted in three modules at three strictnesses and enforced in none, so the same stored value got three verdicts — `'7:30'` sorted after `'19:00'` in the list while `timeOut('7:30', 45)` returned null. The rule is now **lenient about spelling, strict about meaning**: a value naming exactly one real date or time is canonicalised however spelled, one naming none is refused, and nothing ambiguous is guessed. Per §1 the write boundary never rejects — it canonicalises what it can, maps a blank `time_in` to null, and stores the rest unchanged; the read side refuses to compute on a value it cannot read rather than mis-computing. Note the deliberate asymmetry for an impossible date like `2026-02-30`: numbering still places the dive where the diver typed it (numbering never refuses to number a dive), while `surfaceIntervalMin` returns null rather than an interval overstated by 24 hours.
- **`manual_order` stays an integer, and a reorder renumbers the whole date** (owner's call, M1a). Fractional indexing was the alternative — writing `1.5` to drop a dive between 1 and 2, which SQLite's INTEGER *affinity* silently permits — but §6 puts the same schema in Postgres, where an `integer` column does not, so a fractional rank would round or error on its way through `push_changes` and, under whole-row LWW, silently change the diver's hand-ordering on sync. The repository therefore exposes `reorderDivesForDate(db, date, orderedIds)` — whose `orderedIds` must name every live **logged** dive on that date, once each — as the only way to change it, and `updateDive` refuses the field: because `manual_order` is a *tie-break* and hand-ordered dives sort before non-hand-ordered ones, writing it onto the dragged row alone — what `onDragEnd` hands you — lifts that row to the top of its group instead of dropping it where the diver let go. Non-integers are rounded rather than rejected, per §1.
- **A local save failure is shown to the diver; a sync failure is not.** §7's "sync failures never block logging" is about the network, and it must not be read as licence to swallow a failed *local* write. A SQLite insert that fails is a real error the diver needs to see, because the alternative is believing a dive was logged when it was not. M1c's save flow awaits the write, surfaces a failure, and does not reset the form as though it had succeeded; the save control also needs an in-flight disabled state, since the repository is safe under concurrency but a double-tap would create two dives.
- **The primary button stays inverted ink and gains no brand accent** (asked and settled in M1c). The depth scale spans six hues across essentially the whole spectrum, so *any* accent on the `+` lands in or beside a band, and a diver scanning the screen would have to decide whether a coloured object is data or chrome — the exact ambiguity §0.1 exists to prevent. Inverted ink is also already the most prominent treatment available. Ponor's brand colour is the depth gradient itself, which lives on the icon and splash where there is no data to confuse it with. If the `+` ever needs more presence the levers are size, shadow and clearance — never hue.
- **Search floats at the bottom, not the top** (§0.6, M1c). At the top it was the brightest object in the app and the furthest control from the thumb — and §0.5 had already said the primary action belongs in the bottom third, which the `+` obeyed and search did not. Three earlier proposals all argued about how *loud* the field should be; the position was the actual problem. The shape was measured off iOS 26 Messages on a simulator rather than recalled, which corrected three wrong assumptions: there is no bar, it does not span the width, and a shadow rather than a border separates it.
- **Computed values are prefixed `=`, not marked with a square** (§0.6, revised during M1c). The first build used a 6 px outlined square, and the owner — who had approved it in the mockups — read it in the running app as a broken glyph rather than a mark. An equals sign says what the value *is*: the result of a calculation. A symbol that needs a legend has already failed; this one needs none.
- **The depth value anchors a dive row** (§0.6, added after M1b). The built screens obeyed the token system without using it — everything one size, the depth colour reduced to a small trailing number — so the palette never actually read. Depth is the value that differs dive to dive and the one the scale exists to encode, so it is the largest thing in the row. Beat giving every row a depth-tinted edge, which would have spent colour on chrome rather than data.
- **The depth scale ends at band 6 and does not gain more hues.** Band 6 is everything from 40 m down, so a 75 m dive renders as one colour. That follows the physics the scale is built on — below roughly 40 m water has stripped all the colour there is — and six bands are frozen in `DepthScale` / `DepthBand`. Charts instead **darken within band 6** as depth increases: same hue, more resolution, still literally true. The number always carries the exact figure, so only the hue saturates, never the information.
- **MOD is per cylinder, and there is no single "dive MOD".** `tanks` is an array and the app is explicitly multi-gas, so a dive with a bottom mix and a deco gas has two limits — 67.8 m and 18.0 m are both true, and averaging them or taking the first is a fiction. (M1b shipped `mod(dive.tanks[0]?.o2Pct)`, which showed one and hid the rest; fixed in M1c.)
- **No "you exceeded your MOD" warning while a dive has more than one gas.** With a single cylinder the check is sound — max depth against that mix's limit. With several it is not, because which mix was breathed at depth cannot be known without gas-switch times, and `tanks` stores none. UDDF carries them, so the warning waits for sample import and stays gated on `tanks.length === 1` until then. Same rule as §0.4: the app does not warn about what it has no data to know.
- **No schematic dive profiles** (§0.4): rows show the coloured depth number, and the sparkline and detail chart appear only for dives carrying a real sample series. An interpolated curve would read as recorded data.
- **`SectionList` rather than FlashList** (M1b; revises §4's UI row). A personal logbook is hundreds of rows, not thousands, so FlashList's extra virtualization headroom buys little; `SectionList` gives the Dives list its trip sections and their headers for free, where FlashList would need them hand-rolled; and it ships with React Native itself rather than being another third-party bet on New Architecture support — exactly what cost M0 its NativeWind rewrite, above. Revisit if a real logbook's list ever gets slow enough to need it. **One line of this reasoning has since expired and the conclusion has not**: sticky headers were named here as part of what came free, and M1k switched them off (below). Sections, grouping and headers are the rest of it, and they are the part that was doing the work.
- **Hand-ordering is move-up / move-down, not drag** (M1b, owner's explicit call; implements §2.5). It only ever applies to a handful of untimed same-day dives, typically two or three rows, where arrows are both accessible and testable without simulating a gesture. `reorderDivesForDate(date, orderedIds)` already takes an ordered id array regardless of how the diver produced it, so a drag implementation could replace the arrows later without touching the data layer — the interaction and the write are already independent.
- **A trip is one dive centre, with gaps of up to 3 days** (owner's call, revised during M1d; replaces “consecutive days, same place” in §3). The original rule keyed on the *site* and allowed one day, and both halves broke on the ordinary shape of a diving holiday: a boat day out of Subic visits two to four different wrecks, so one week fragmented into a dozen one-dive “trips”, and a single rest day split whatever survived. The dive centre is the thing that stays constant across a trip's sites, and carry-over prefill (§2.1) keeps it filled without retyping, so grouping on it is both correct and free. Because the centre *is* the grouping key, every dive in a trip shares it by construction — so the header is simply the key, with no “most-dived site” heuristic and no “5 sites” fallback to invent. A dive with no centre still falls back to its site, so shore diving groups exactly as it did before. Rejected: dropping the place condition entirely (a week of local diving merges into one meaningless group); and a site hierarchy putting every Subic wreck under “Subic”, which needs a region level that neither the local schema nor §6's `dive_sites` has — that waits for the community catalogue in M2.
- **"Up next" is distinguished by ink, not by shape** (§0.6, added during M1d). Rendered identically to a trip header it said the two were the same kind of object, when one is a filed record and the other a live queue of dives still to come (§2.4). The discriminator in code is an explicit `variant` prop, never `title === 'Up next'` — that string is a label bound for i18next (en + cs), and a rule reading it would stop firing silently the day it becomes `Další v pořadí`. Same reason `splitPlanned` keys on `status`, not on a display string.
- **Date and time are pickers, so an invalid value cannot be entered** (owner's call, M1d). This resolves an open tension rather than splitting it: `date` carried the form's only blocking rule, so a mistyped date was the one thing that could refuse a save — squarely against §1 — while §10's own range decision says the form warns and never rejects. Both answers on the table were bad: keep rejecting and contradict §1, or accept an unparseable date and hand the domain a value it cannot compute on. A picker removes the case instead of adjudicating it. `timeIn` gets the same treatment for a quieter version of the same defect — a typo there does not block the save, it silently drops the dive out of time-ordering and voids its surface interval. **The Zod rules stay** as the domain's backstop: the UI can no longer produce a bad value, but M2 sync will deliver rows this form never touched, and removing a guard because one of its callers got safer is not the same as removing dead code. The stored form is still the `YYYY-MM-DD` / `HH:MM` string — `domain/datetime.ts` remains its only owner, and the `Date` the picker returns is converted there from LOCAL components, never `toISOString()`, which would store the UTC day and shift any dive logged late in the evening east of Greenwich to the day before.
- **A dive's status changes in exactly one place: the form's own Logged/Planned control** (M1d, closing §2.4). Every *consumer* of a planned dive shipped first — "Up next", exclusion from numbering, the *Complete dive* pill, the completion flow — while the producer was never built, so no diver could create one and the planned dive in the dev database was seed data. The control is a plain form field, which is what makes the rest fall out: the patch names `status` exactly when the diver moved it, so **editing a planned dive leaves it planned and flipping the control to Logged *is* completing it**, one control doing both jobs. What it replaces is a rule inside the form that logged any planned dive it was handed — found by using the app: correcting a typo in a planned dive's site name silently completed the dive. *Complete dive* therefore passes the state the control should **open** on through the route (`openAs`), never a second write path from the list. Two consequences worth stating: **the heading reads what the save will do**, not what the dive is, so "Complete dive" appears only when the control is on Logged over a stored plan (it used to be permanent, and true only because the save quietly made it so); and the control is §0.6's quiet chip vocabulary in the form's header row, deliberately **not** a sixth field in §2.2's core strip, because a status is not one of a dive's measurements. **A planned dive's date is not constrained** in either direction — a plan becomes past-dated by the clock moving (plan three dives on a boat, do two, and at midnight the third is past-dated with no diver involved), so a minimum date would be a rule time itself violates.
- **A destructive confirmation is OS chrome; the app's own control stays muted** (M1d, deleting a dive). §0.1 reserves colour for depth, which leaves nothing to make "Delete dive" look destructive — and a plain muted label is exactly right for a control you should not hit by accident. The weight goes into the platform `Alert` that follows, whose `destructive` button is red because iOS draws it that way. The app's surfaces stay monochrome and the diver still gets the standard danger signal, on the same reasoning that lets the keyboard be full of system colour. Deletion is **soft**: the row survives with `deleted_at` set, because M2's sync needs the tombstone — a hard delete would satisfy a "the dive is gone" test and silently break sync later. That test existed and passed against a hard `DELETE`; it now asserts the surviving row.
- **A dive's own actions: *Edit* in the top bar, *Complete dive* and *Delete dive* at the end of the content** (owner's call, M1d). The top-right action is *Edit* for every dive, planned or logged, and always opens the form on the dive's own status. The two acts that change what a dive *is* group at the end of the content, where *Delete* already sat deliberately rather than beside *Edit*. What this replaces: a single top-right control that read "Complete dive" over a plan, which left a diver fixing a typo with no button matching their intent. Completing does not get quieter — the prominent pill on the "Up next" row is the on-the-boat path and is untouched. *Complete dive* wears §0.6's bordered pill, the same treatment this same action already has on that row; it is not destructive, so it does not borrow *Delete*'s plain muted label, and it is not the screen's primary action, so it is not the filled button. **The recurring defect here is a label and a link that disagree** — twice a "Complete dive" control was wired to the plain edit route, completing nothing while saying it did. A test naming only the labels passes with the two routes swapped, so the assertion that counts is which href each control sends.
- **Two §1 edges that only become reachable when sync does** (recorded at the end of M1d, to decide in M2, not before). First: a dive arriving from a newer client with a `status` this build does not recognise. The other unknown values are now kept and flagged, but `status` cannot be — it is non-nullable (§6) and drives `splitPlanned`, dive numbering and "Up next", and the form's control is two-state, so there is no way to show it without choosing one. Refusing the save breaks §1; choosing silently rewrites the diver's data. Decide it against a real sync payload rather than in the abstract. Second: a kept-but-unrecognised option value renders as **nothing** on the dive detail — `formatEntry` and its siblings return null for a value they do not know, so the row is simply omitted. That makes "flagged" only half true today: the value survives the round trip but the diver cannot see it. Both are unreachable until M2 delivers a payload this client did not write.
- **`carryOverDate` broke twice, and both times its tests agreed with it** (M1d). Six lines, two defects. First it compared a real instant against a UTC-midnight calendar value, so §2.1's window was 48 h *plus the device's UTC offset* — a dive two days old in Manila still carried its date forward. Fixed, and then the same function shipped a one-sided comparison: a previous dive dated in the **future** produced a negative difference, which is also "less than a day", so completing a dive planned for next week made every later dive default to next week. Both were found on a device, not by the suite, and in each case the existing tests had been written to match the behaviour rather than the intent — the second fix had to rewrite four tests that were standing on the bug, one of which used the year 2099 precisely because the window had no near end. The lesson is not about dates: **a test written after the code, from the code, agrees with the code.** The window is now stated as a closed interval — today or yesterday — because "less than 48 h old" is the phrasing that hid both halves.
- **Two domains, and the browser build constrains where the app half can live** (registered during M1). `ponor.app` and `ponor.online` are both held. The natural split is a marketing site and store links on one, and the web app itself on the other — but that is not merely branding, because **the web app cannot be hosted anywhere that will not set response headers.** wa-sqlite needs `SharedArrayBuffer`, which needs cross-origin isolation: `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (§9). Netlify, Vercel and Cloudflare Pages all allow custom headers; **GitHub Pages does not**, so it cannot serve the app however convenient it looks. A static marketing page has no such constraint and can live anywhere. Decide which domain takes which when the web build is actually deployed — the point of recording it now is that the constraint is on the *host*, not on us, and it is invisible until the page loads and the database silently fails.
- **Four unit pairs, and deliberately no fifth** (M1, implementing §3's Settings list). m/ft, bar/psi, °C/°F, kg/lb — SI is stored, always, and conversion happens only at display. **Cylinder volume stays litres in both systems**: the imperial counterpart is cubic feet *at working pressure*, which is not a conversion of litres at all but a different quantity derived from two values, so an "80" is not 11.1 l converted, it is a different way of describing the cylinder. Offering it as a fifth toggle would silently produce wrong numbers. Duration stays minutes, and a gas fraction stays a percentage.

**Precision is decided per pair, not mirrored.** Depth keeps one decimal in metres, because a decimetre is meaningful, and takes **whole feet**, because a tenth of a foot is three centimetres of false precision. Pressure is whole units in both. Weight carries a decimal only when it has one, since weights are set in half-kilos and a fixed count would render a plain `6 kg` as `6.0 kg`.

**A display rounding may never rewrite stored data.** Opening a dive in imperial and saving it untouched must leave the stored SI value byte-identical and `updated_at` unmoved — a round trip through a rounded display figure would quietly erode every dive a diver ever re-opened, and under M2's whole-row last-write-wins it would propagate. Verified live, not assumed: `24.6` stayed `24.6` and the row was not written. The form therefore shows the raw stored value where the detail screen shows a rounded one; that asymmetry is the point, not a bug.

The **Settings screen owes one thing here**: it must write the preference through `setUnitSystem`, never by touching the `settings` row itself, or the read and the write stop agreeing (§4.1).
- **A screen's top clearance is the device's, never a constant** (M1). The shared `screen` style used a flat 48 pt. On an iPhone 17 Pro the safe-area inset is 62 pt and the Dynamic Island's bottom edge is at 50.67 — so the search screen's list began **2.67 pt underneath the island**, and Settings' title sat 7 pt above the safe line. Only the Dives bar had been fixed, because that is where the owner noticed it, which left the app disagreeing with itself across five screens. The fix was **one owner** — `screenTopInset(safeAreaTop)`, already written for the Dives bar and generalised rather than copied — not a second helper. Two details worth keeping: the constant looked right on every simulator screenshot anyone had taken, because a back control's own 48 dp centring pushed its *ink* down far enough to look deliberate while its container sat too high; and the numbers here were settled by pixel-scanning 3× screenshots against Apple's own apps, after eyeballed readings carried a consistent 4 pt error.
- **Duplicate-a-dive is cut from v1** (owner's call, M1e; removes a §2.1 bullet and part of §9's M1 line). §2.1 offered it as "any past dive can be copied as a starting point", written before carry-over prefill and the trip grouping were built. Once they were, the feature had almost nothing left to do: every new dive is already prefilled from the previous one, and the previous one is the dive a diver overwhelmingly wants to copy — so duplicate's only unique job was copying a dive that is *not* the most recent, which is the rare case, and the one where a stale depth or duration is most likely to be wrong. It is not shelved to §9's post-release list either: the version worth building later is an explicit "copy from…" picker, which needs M2's site catalogue to be worth opening. Cut, not deferred, so nothing is left half-promised.
- **A preset holds cylinders and gas, and nothing else** (owner's call, M1e; narrows §2.1 and §6). The table was specified as "cylinder/gas/suit/weights", and the other half of that list was the half that did not need it: suit, hood, gloves, boots and weights already carry from the previous dive (§2.1), so a diver who dives dry in a quarry gets them filled without naming anything. A preset that also carried them would be a **second, staler source for fields carry-over already fills correctly** — §4.1's defining defect, arriving as a feature rather than as a copied line. What genuinely varies inside one diver's habits is the cylinder: 12 l steel on the boat, alu 80 on holiday, and a nitrox mix that goes with one and not the other. So the five columns are dropped from `gear_presets` in a migration rather than left unwritten, because a column DESIGN.md no longer describes is exactly the drift this project keeps paying for. **The pressures are not stored either**, on precisely §2.1's reasoning for carry-over: a preset that filled in 200 bar would be inventing a reading. One rule strips them, shared with carry-over's own — not a second copy. **A preset is captured in the form and edited in Settings** (owner's call): saving one takes whatever cylinders are already typed into the dive you are logging, because retyping them in Settings is the work the preset exists to remove — and §3's Settings list is then a real editor, name and cylinders both, not a list of names with a delete button. The editor is its own route and its own screen rather than an expanding row, so a preset is edited the way everything else in this app is edited: a list, a route, a form, a save.
- **Autocomplete matches plain substrings in M1, and fuzzily in M2** (M1e, implementing §2.3's own split). Own history only, since the community catalogue does not exist yet; site, centre, buddy and guide, which is exactly the four §2.3 names. Two things are deliberately absent and both belong to M2, where §5's `pg_trgm` arrives and site search is reworked around the shared database: diacritic folding, so a Czech diver typing `zelezna` does not yet find `Železná`, and the "did you mean" near-match check that stops duplicate sites. Building either now means building it twice, and §0.6 already froze the same boundary for the list's *styling*. **What M1 does owe is the id/name pair.** §6 stores a site as `site_id` + `site_name` snapshot, so picking a suggestion sets both together and typing over a name clears the id — otherwise a dive carries one site's id under another's name, which is latent while every id is null and becomes wrong the day M2 fills them in.
- **A preset's name is its identity, and the refusal to duplicate one is best-effort** (M1e). Presets sort by name, and saving a second preset under a name already taken is refused rather than silently making two rows a diver cannot tell apart in a chip row. What that refusal is *not* is a uniqueness constraint: M2's `pull_changes` can deliver a preset created under the same name on another device, where no local check was ever consulted, and §7's whole-row last-write-wins has no opinion on names. So the ordering comparator carries a `createdAt` tie-break — two presets sharing a name still sort deterministically on every device rather than swapping places between renders. The refusal is a courtesy to the diver in front of the screen; the tie-break is what keeps the list stable when the courtesy has been bypassed by a device that was never asked.
- **The editor converts against the stored cylinders, not against the raw form values** (M1e, and it is the same rule §10 already states for dives: "a display rounding may never rewrite stored data"). Converting the editor's fields back to SI unconditionally is the obvious implementation and it is wrong: an imperial diver who merely *opened* a preset and pressed save would rewrite a stored 232 bar as 232.00858…, because 232 bar renders as 3365 psi, and 3365 psi converts back to a number that is not quite 232. That is not a rounding artefact to shrug at — under §7's whole-row last-write-wins keyed on `updated_at`, a save that changed nothing would then **beat** a real edit made on another device. The conversion therefore pairs each cylinder with the one stored at the same index and keeps the stored value when the displayed figure still represents it, exactly as `toDivePatch` does for a dive. Verified in a browser against a real database, not reasoned: 3365 psi in, save untouched, `232` back in the metric form.
- **The editor edits every cylinder a preset holds, though it shows one** (M1e). The form's cylinder block is single-cylinder until "+ add cylinder", and a preset built from a twinset plus a deco stage holds two. An editor that wrote back only the cylinder it displayed would have silently deleted the second one on any save — a data loss with no error, no visible change, and nothing on screen to suggest it had happened. The cylinders past the first ride through untouched.
- **A preset a diver is offered to author must hold at least one cylinder** (M1e). The app refuses to save a preset whose cylinder block records nothing — in the dive form's capture and in §3's editor alike — because such a preset is a chip that *blanks* the diver's cylinders, which is worse than no chip at all. What the rule is **not** is a uniqueness- or NOT-NULL-style constraint, and the distinction is the one the duplicate-name entry above already draws: `createGearPreset` stores whatever it is handed and M2's `pull_changes` writes rows this client never composed, so a cylinderless preset can *arrive* — and everything that reads one tolerates it, since §3's list omits the summary rather than drawing a dash, and applying one blanks the block rather than throwing. **Tolerating what arrives and refusing what a diver is offered to make are different questions**, and only the second is answered here. §1's "never block a save" is about a *dive*; a preset the diver is composing is the same kind of object `setDivesBefore` already refuses an impossible value for. The refusal is asked of the cylinders **as they will be stored** — pressures already stripped — because a cylinder holding nothing but a gauge reading looks completely full on the form and stores nothing at all.
- **A screen with no answer must not state one — and the loading signal deliberately does not follow the error split** (M1f). `useDives` and `useGearPresets` both handed callers an empty array before their query had run, so three screens asserted things that were false for a frame: "Dive not found." over a dive that was there, a blank edit form over a real dive, and — loudest of the five — "Log your first dive" over a logbook with eleven of them. An empty array cannot distinguish *nothing there* from *not looked yet*, so both hooks now carry `resolved`, and a screen without an answer renders its frame and its way out rather than a sentence. **The mechanism is `updatedAt`, not `data`**, and that is the part worth recording: drizzle's `useLiveQuery` seeds `.data` with `[]` for a `db.select()` builder, so a `?? []` that three docblocks described as covering the first render had in fact never once fired, and a fix keyed on `data` would have compiled and done nothing. **On the split:** §4.1's entry for `useDives` records why its two *errors* stay independent — merging them let a failed settings read blank the whole logbook. The loading signal faces the same fork and answers it the other way, deliberately: it reports on the dives query alone, because merging the two *loading* states would be the identical defect one render earlier, a display preference deciding whether the dives appear at all. The cost is stated rather than hidden — a logbook whose settings read lands late numbers from offset 0 for a frame and then renumbers. A number that corrects itself is the smaller harm than a list that is not shown. **Why this was worth doing before M2 rather than during it:** today the flash is brief and the answer that follows is always "it was there", but sync makes first reads slower *and* makes "deleted on another device" a real answer, so the screen telling a short-lived lie starts telling a plausible one.
- **A third §1 edge that only becomes reachable when sync does — the preset editor's `units` race** (found at the end of M1f, to decide in M2, and a sibling of the two edges recorded above). Measured, not theorised: a preset draft holding a name and a size reverts **wholesale** to the stored preset when a late `units` answer lands, while the pressure correctly converts. The loss is total, not partial. **What holds it shut today is not a property of any module**, which is why it is written down rather than left to be rediscovered: `setUnitSystem` has exactly one caller, the Settings screen, and the editor is a route pushed *on top of* Settings — so no gesture can change units while the editor is mounted, leaving only `useUnitSystem`'s own first answer, which resolves inside a frame on a local read. §7's `pull_changes` is the **specified** second writer, and the day it exists this is the `dives_before` defect again (§10, "a screen with no answer must not state one" — the half of it that destroys input rather than merely displaying a false one).

> **It is not patched now because the fix is a design decision, not a patch.** Converting the draft rather than rebuilding it is the obvious shape, and it does not work as written: `toStoredTanks` runs a cylinder through `safeParse` and returns `[]` for a draft mid-keystroke — `"1."`, `""`, `"abc"` — so a live draft cannot round-trip through SI. And the two screens that already face this question **answer it two different ways**: the dive form keeps the diver's figure and lets the label change under it (the silent mislabel `SeedState.units` names), while the editor converts the figure and discards the draft. A third screen inventing a third answer is how the "one rule in two places" family started. Decide it once, for all three, against a real sync payload — the same instruction the two edges above carry.
- **A stale failure is the same lie as a stale absence** (M1f/M1g, completing the entry above). `useLiveQuery` sets `error` only in its failure paths and never clears it, so every notice keyed on one outlived the failure it reported — for the life of the component. Three fields carried this, not the one that was noticed: the `dives_before` banner it was found on, and the two that matter more. `useDives.error` is **fatal** on the Dives screen, so a transient failure blanked a logbook that had since been read perfectly well; and `useGearPresets.error` is what the preset editor dispatches on to choose between "couldn't load" and "may have been deleted", so a recovered read now tells a diver the honest one. Fixing the site that was reported and leaving its two siblings would have been §4.1's defect performed deliberately.
- **A render-phase gate makes the code before it converges both unreachable and unkillable** (M1g, and this is a fact about *this codebase's* dominant pattern, not a general one). Several screens adjust state during render rather than in an effect — React's own prescribed shape, and this repo's ESLint config rejects the effect-plus-`setState` alternative outright. The consequence nobody had written down: React **re-runs** a component whose render scheduled its own update and discards everything the first pass produced, so a branch written to handle the not-yet-converged render can never be observed *and can never be mutation-tested* — deleting it changes no test, which looks exactly like a test gap and is not one. The remedy is to delete such a branch rather than defend it, and the discipline is to notice which one you are looking at: **a mutation that survives is either an undefended guarantee or a genuinely unreachable one, and only reading the mechanism tells you which.** Seven undefended guarantees were found this milestone by mutation; this is the one case where mutation's answer was "there is nothing here to defend".
- **The two cloud variables must be read as literal `process.env.EXPO_PUBLIC_*` member expressions, and that is not a style preference** (M2). Expo's Babel preset inlines only what it can *see*: in development it rewrites those expressions to `expo/virtual/env`, which really is `process.env`, so any shape works and every simulator run passes; in a **production** build it substitutes string literals at build time and leaves a bare `process.env` untouched — and a shipped bundle has no dotenv to fall back on. So the tidier, more testable `readCloudCredentials(process.env)` passes every test, passes every dev run, and **ships a store binary with no backend at all**. Measured, not feared: that swap leaves 18 of 20 tests green. The covering test therefore runs the real file through this repo's own `babel.config.js` in production mode, because nothing observable inside Jest can tell the two apart. It is the same family as §9's `openDatabaseSync` finding — a mechanism in the toolchain, invisible from the code, that only fails where you cannot watch it.
- **A missing backend is a value, not an exception** (M2). §1 makes the account optional — the whole app runs offline from on-device SQLite, and M1 shipped and met its done-when with no backend in existence. So `cloud/supabase.ts` returns *unconfigured* as an ordinary answer a caller can check, and the proof it does is that the entire suite stays green with no credentials anywhere. **`db/client.web.ts`'s throwing proxy looked like the same problem and is the wrong precedent for it**, which is worth stating because the resemblance is close enough to copy by accident: there, a database that failed to open means the app genuinely cannot function and throwing is the honest report; here, no backend is the *expected* state for every diver who has not signed in. Absent, blank and whitespace-only are one answer, because a half-filled `.env` line — `EXPO_PUBLIC_SUPABASE_URL=` with nothing after it — is what a real one looks like mid-setup.
- **A cylinder's specification is snapshotted onto the dive** (M1h, owner's correction). A preset fills the fields; the dive keeps its own copy. Editing "Alu 80" next year must not silently rewrite what a dive two summers ago recorded — the identical reasoning §6 already applies to `site_id` + `site_name`. **Storing and showing are different questions**, which is what makes this compatible with the complaint that produced it: the form summarises the captured spec in one row rather than presenting six fields nobody touches, and expands when a diver wants to correct it on this dive.
- **Material and configuration are two facts, and `count` is derived from the second** (M1h). A cylinder is steel or alu; a rig is single, twinset or sidemount. Bundled into one chip row — as the first design sheet drew it — "twin steel 12" is unsayable and a sidemount rig cannot state what it is made of, which is precisely the setup a starter preset wants to offer. Splitting them also answers the owner's "why is there a Count field": nobody types a count any more, because the configuration says it. Twinset and sidemount both mean two cylinders and are not the same rig, so the distinction is real rather than cosmetic.
- **Nitrogen is computed, never stored** (M1h). O₂ + He + N₂ = 100, so two numbers describe every mix a diver will log: heliox is N₂ = 0, and air's ~1 % argon is conventionally counted as nitrogen exactly as every dive planner counts it. Storing the third would be a third home for one fact and a row that can disagree with itself. It is *shown*, with §0.6's muted `=` prefix, beside surface interval and RMV.
- **A rebreather is not a gas mix, and it is out of v1** (M1h). It appeared in a mix row beside AIR and TRIMIX, where it cannot be right: a rebreather is a delivery system running a *diluent* under a controlled PO₂ setpoint, so a CCR dive needs a mix **and** a setpoint to be recorded honestly, and "REBREATHER" as a mix records less than nothing. Out of v1 rather than half-built — the owner dives open circuit, RMV means something different on a loop, and the post-release shelf is where it belongs. The same reasoning parks **argon for drysuit inflation**: that bottle is not breathed, so its percentages are not a mix, and it needs a cylinder *purpose* concept that v1 has no other use for.
- **Visibility and weight each carry a judgement and a number, deliberately** (M1h). Nobody measures visibility, so the scale (high · average · low) is the primary and metres is an optional refinement for divers who estimate. Weighting is the sharper case: `6 kg` means nothing on its own, and *"6 kg, and I was over"* is the fact a diver actually uses to dial in the next dive. **These are two encodings of one subject and that is intended** — recorded here because §4.1's instinct is to unify look-alikes, and a later reader who unifies these deletes the half that carries the meaning.
- **Water body stays; `brackish` goes — and the difference between those two is the entry** (M1h). The design sheet marked *water body* "not in v1" and drew salinity as SALT · FRESH, but both shipped in M1c and their columns hold data, so **not building a field and removing a shipped one are different acts**: the second needs a decision about every row that already holds the value. Put that way, the two answers came out differently. Water body keeps all six values and its "not in v1" label is read as *not yet styled*. Salinity loses `brackish` on the owner's explicit call — the diver's real question is salt or fresh, and the estuary case did not earn a third chip. The point preserved here is not the outcome but the discipline: a shipped field is removed **deliberately and by name**, never by inheriting a label from a design sheet.
- **Suit, thickness and accessories are three fields, because exclusivity is the discriminator** (M1h, owner's call — this **overrides** the same day's ruling that equipment would be deferred). The design sheet put wetsuit thicknesses, drysuit, hood, gloves, torch and camera in one multi-select, which is the cylinder row's mistake in different clothing: **you wear one suit and any number of accessories**, so an exclusive choice and a non-exclusive one were sharing a control. They split into `suit` (which keeps `semidry`, that the sheet had dropped), a separate `suit_thickness_mm`, and a token set for the rest. **Thickness is a number, not a token**: a list offering 3 mm and 7 mm makes a 5 mm suit unsayable, and a diver forced to pick the nearest wrong value is the failure §1 exists to prevent. The accessories are a token set rather than more booleans for the reason §6 already gives for `tanks` — adding "camera" must not cost a column.
- **The migration history is collapsed to a single `0000`, once, and this window closes the first time Ponor runs on real hardware** (M1h, owner's call; he confirmed the app has never been installed on a device, only a simulator and a browser). `0000` plus `0001` plus the three or four this redesign would have added are all records of correcting a schema that never left a laptop — permanent noise in the file M2's sync protocol will be read against. A single honest migration describing the schema as it actually is, is the better artifact. It is **`0000_thin_warpath`**, named here because the old file names are gone and nothing else records it. **Two databases are reset by this, not one**: the simulator's `ponor.db` and the browser's OPFS store, which also holds real test dives. **The moment a build exists on a phone — the owner's, TestFlight, anyone's — this liberty is gone for ever** and every schema change costs a migration, because from then on there is data nobody can reach to reset. Recorded so that a later reader who finds one tidy migration does not conclude the project is casual about them.
- **A patch that diffs by identity writes every array field on every save** (M1h, found by an implementer looking somewhere the brief never pointed). `Object.is` on two arrays is *always* false, so a field holding a list — `tanks`, and now `equipment` — is "changed" on a save where the diver touched nothing. That is not a wasted write: it advances `updated_at`, and §7's whole-row last-write-wins is keyed on that column, so the device that changed nothing **beats** the device that changed something. It is the identical hazard `updateDive`'s empty-patch guard and the editor's convert-against-stored rule already exist for, arriving through a third door. Every list-valued field needs an explicit comparison in `toDivePatch`, and **`equipment`'s compares as a *set***: `hood, gloves` and `gloves, hood` are the same equipment, and treating order as meaning would reintroduce the bug it was written to fix.
- **Nitrogen is computed whenever O₂ is known, and a blank helium means zero** (M1h). The first spec said "null when either input is missing", which is defensible in the abstract and wrong in a logbook: **nobody writes "He: 0" for air**, so that rule showed the figure only on trimix — the one case where a diver least needs the app's help. Absent helium is therefore read as none, and an air dive reads N₂ 79 as every dive planner shows it. **The cost is named rather than hidden**: a trimix diver who records O₂ and omits He gets a nitrogen figure that is too high. That is the smaller harm — it needs someone to log a helium mix and then not say how much, against a rule that otherwise blanks the value on every air and nitrox dive ever logged — and the figure carries §0.6's muted `=` prefix, so it already reads as something the app worked out rather than something the diver stated.
- **An unrecognised cylinder configuration counts as one cylinder, and that is a ruling rather than a fact** (M1h). `countGas` reads a rig's cylinder count to multiply gas by, and its docblock argued that no value is both *recorded* and *impossible* — which is true of the values this app writes and not true of the ones §7's `pull_changes` will deliver from a newer client. So a configuration this build does not recognise counts as **one**, which **understates** the gas used. That is the direction `derived.ts` itself calls unsafe, and it is still the right trade: the alternative is refusing to compute at all, which blanks the RMV of a dive whose data is perfectly good apart from a word this build has not learned yet. Understating is also the conservative direction for the number a diver reads — a low RMV looks like good air consumption, not like more gas than you had. Recorded here because the code said it as an observation, and it is a decision with a cost. It joins §10's other "edges that only become reachable when sync does": decide it against a real payload, not in the abstract.
- **Converting once and comparing is wrong wherever a stored value is matched against a typed one** (M1h, and this is the *third* door onto the rule §10 already states for the preset editor). *Save as preset* hides itself once the cylinder block matches a preset the diver already has — and for an imperial diver it never matched, because 207 bar renders as 3002 psi and 3002 psi converts back to 206.98…, so the comparison failed against the diver's own saved cylinder. The control simply never disappeared for anyone working in feet and psi. The fix is the same shape as the editor's: **convert per candidate, against the stored value being compared to**, never once into a canonical form and then compared. The recurring lesson is that a unit round trip is *not* an identity, so any equality test that spans the display boundary must be built from the stored side outwards.
- **`react-hook-form` mutates the `tanks` array in place, so a `Controller` on that path silently stops re-rendering** (M1h). After any `setValue('tanks', …)` — which is exactly what applying a preset does — a `Controller` watching `tanks` sees the same array reference it saw before and does not update. The visible consequence: apply a preset, then edit a cylinder field, and the summary row **freezes** while the values beneath it change. Nothing throws and no test that renders once can see it. `useWatch` subscribes to the value rather than the reference and is the fix. This is the same family as `useDives`' memo note — *identity is not a contract* — arriving from the library's side instead of ours, and it is worth knowing before the next component watches an array-valued field.
- **The chevron means "there is more underneath", on a group header and on a field row alike** (M1h). §0.6 introduced it for collapsible groups; the cylinder summary row now carries one too, because that row hides its spec fields exactly as a group header hides its rows. That is an extension of one mark's meaning rather than a second meaning for it — the affordance answers the same question in both places, and a diver who learns it on a group has already learned it on the row. What would be a collision is using it for anything that does *not* expand.
- **A screen's BOTTOM clearance is the device's too, and the tab bar is part of it** (M1h). §10 already records the top edge — "never a constant", after a flat 48 pt met a 62 pt inset. The bottom edge had the identical defect, the identical number, and one thing more in front of it: `emptyStateWrap` padded 48 while the real clearance inside the tabs is **83** — 34 pt of home indicator plus a 49 pt `UITabBar` — so *"Log your first dive"* rendered **underneath the glass**, its label an illegible smear and only its ends reachable. **`useSafeAreaInsets().bottom` does account for `unstable-native-tabs`**; that was measured on a device (83 inside the tabs against 34 on the dive form, which is a root Stack *over* them), not reasoned about, and it is why the fix is an inset and not a hand-added bar height. The owner is `screenBottomInset`, a sibling of `screenTopInset` rather than a second helper — two screens live under that bar and both answered it with a constant. **The inset alone is not enough**: the safe-area line *is* the bar's top edge, so an inset-only version left the button touching the glass, and the same 24 pt gap `formFooter` already uses for the same object was added over it.

> **What made this survive is worth more than the fix.** The development database has held dives since M1a, so the empty state had **never once rendered on a device** — and no unit test can see a layout fact about a real tab bar. It was found the day a migration collapse emptied the database, by looking. The populated list had the same defect one row down (`listContent` padded 24 into an 83 pt inset, so the last dive sat under the bar), and *that* was invisible until eight rows were seeded to make the list scroll. **Both cost a deliberate act to make visible, neither cost a test.** This is the standing lesson of §9's M1 note in its purest form: a green suite has been wrong here repeatedly, and the empty state is exactly the branch nobody's development data ever reaches.
- **Renaming a value out of a vocabulary is not removing a shipped field, and the difference is who wrote the row** (M1h, on `partly` becoming `cloudy`). `brackish` needed a ruling because dives already held it. `partly` did not, and the check was **made rather than assumed**: the `weather` column landed earlier in this same milestone, against a database this milestone had already reset, so no row anywhere has ever held the word. What is worth recording is what a stored one *would* have done — read as **not recorded**, carrying `unknownOptionNote`'s sentence, which is §10's answer for a value arriving from a client this build does not know. **That answer would have been wrong here**, because the value would have come from *this* build two commits earlier, not from a newer one. The rule that falls out: *kept and flagged* is right for a value you have never seen, and wrong for one you yourself wrote and then renamed — a rename inside one milestone owes a migration or a proof that no row holds it, and the proof is cheaper only while the answer is genuinely zero.
- **A chip vocabulary may be numeric, and that is not the literal-union narrowing rejected above** (M1h). Waves, current, surge and rating are integers, and `OptionChips` was `<T extends string>`. It widened to `<T extends string | number>` rather than the scales being stored as digit-strings — which looked free, since `optionalNumber` already coerces at the write boundary, and is not: `domain/types.ts` **derives each type from its own list**, so a digit-string list yields `type WavesLevel = '0'|'1'|'2'|'3'`, a string type standing for an integer column, and the next reader writes `dive.waves === '2'`. **The two entries only appear to disagree.** The rejected narrowing is about `Dive['waves']` — the *column*, which stays `number | null` precisely so a future client's `rating: 6` is representable. `CONDITION_SCALE_VALUES` and `RATING_VALUES` are the *chip vocabulary*: what this build offers a diver to tap, not what the column may hold. A value outside the vocabulary is still stored, still read back, and now flagged rather than silently unrepresented.
- **A guarantee that rests on a type is only as wide as what is in scope** (M1h, recorded because the honest version is more useful than the flattering one). The tab layouts could pass a raw symbol where a resolved per-platform name was wanted, and the browser would then look for a web name, find none, and draw nothing — invisible to Jest, because `src/app/` carries no tests, and **also invisible to `tsc` and to lint**, since `SymbolView` accepts the raw shape perfectly happily. It was invisible to all four gates and to every simulator run, because the simulator is iOS and iOS was the one spelling that was right. The fix moved the wiring into `navigation/tabs.ts` and hands each layout an item built **field by field**, so it carries no raw symbol at all and the mistake stops compiling — which is how a rule reaches a tree that cannot hold a test. **The boundary is stated where someone would cross it:** `SymbolView` still accepts a bare symbol, so the protection is that the layouts no longer *hold* one, and a future file that re-imports the raw routes would compile fine. That is a rewrite rather than a slip, and it is worth knowing that this closed one instance rather than the class — `src/app/` is still untestable, and "the layouts are thin enough now" is a judgement, not a gate.
- **A cleared row aligns with a never-carried row, not with a carried one** (M1h, measured rather than chosen). Grouping the mark with the ring pushed a carried value's right edge from 80 pt to 96 pt off the trailing inset, while `— cleared` still ends at the 20 pt inset like every untouched row — so the step between them grew from 60 pt to 76 pt. It was predicted to shrink; it did not, and the reason is that the step *is* the absence of a trailing control, so widening that control widens the step. **It stays.** Rows carrying a control step aside for it and rows without one do not, which is the same rule the rest of the form follows; and the only way to close it is a 64 pt invisible spacer on cleared rows, which would buy alignment with the two or three carried rows on screen and lose it with the twenty that never carried anything. The tag is what says *cleared* — its x position is not, and does not need to be.
- **The core strip shrinks to identity, and the groups that matter open by default** (M1h, owner's call, superseding the eight-field strip agreed hours earlier). Eight always-visible rows was the answer to a real complaint — time in and both pressures were hidden behind a collapse — but it answered it by flattening structure that was doing work. The better shape uses the machinery M1h had just built: **groups remember whether they were opened, so "open by default" is a starting state rather than a special case.** *Date · site · centre* stay always visible, because they identify the dive rather than measure it; **Times & depth** takes max depth, average depth, duration and time in, open by default; the pressures go with the cylinder they belong to. Nothing is hidden that was visible; what changes is that a diver who never records an average depth can collapse the group once and keep that.
- **The chip marks are removed, and a proper icon set is on the shelf** (M1h, owner's call). M1h gave the scales marks that encode their own scale — counted arrows, counting bars — and they worked in the sense §0.6 demands: nothing needed a legend. They were still not good enough to keep, and two costs made that concrete: *Current* and *Surge* wrapped to a second line **because of the marks**, measured (unmarked they fit with room to spare, and each arrow costs ≈29 px); and *Visibility low*, one bar at that size, read as **punctuation** — a full stop before the word. Removing them costs nothing and closes both. **`Entry`'s shore and boat stay**, because they predate this and are the case §0.6 already cites as an icon genuinely carrying meaning. A custom set is wanted and is a design job, not a mark-per-row patch — §9's shelf.
- **The Dives capsule floats beside the title, and the sticky trip header goes** (M1h, owner's call, reversing §0.6's "sibling above the list, not an overlay"). The owner's reason is that at rest a floating capsule covers nothing, and a row passing under it while scrolling is recoverable — you scroll on. That is right about rows and **not right about a sticky header, which parks under the capsule for a whole trip's scroll extent rather than passing beneath it**; that is precisely how the trailing date range came to be observed clipped to "…16". So stickiness is what gives way, not the capsule: trip headers now scroll like everything else. The cost is that a diver deep inside one trip cannot see which trip it is — small, because a trip is two to six dives — and it buys the title the height every other screen's title has. §4's `SectionList` choice survives it: sections, grouping and section headers are what it is for, and stickiness was one line of that reasoning rather than all of it.
- **The pressures stay with the cylinder; the group moves instead** (M1i, owner's call, settling the question M1h's strip reopened twice). The owner wanted start and end pressure back in the always-visible strip — he fills both on every dive, which is the same complaint that produced the eight-field strip — and then found the argument against his own preference before anyone else did: **with a second cylinder, a *Start pressure* row in the strip describes `tanks.0` and says nothing about the rest**, so the strip would show one cylinder's number under a label that claims to be the dive's. A strip that lies about scope is worse than a group that takes a tap. So the fields stayed in *Gas & cylinders* and **the group moved to second, above *Conditions*, opening by default** — the pressures land two rows lower on the screen rather than behind a chevron. Confirmed in build: the strip had carried a ~15-line comment existing only to explain why two of its rows reached into `tanks.0`, and that comment is now gone rather than inverted. The `+ add cylinder` gap (§6) gets easier rather than harder, which is the test this had to pass.
- **"Conditions" means the day, not the place** (M1i, owner's call). *Entry*, *salinity* and *water body* had sat in *Conditions* since the form existed, and the owner asked whether they belonged there at all. They do not, and **§2.1 had said so all along without anyone reading it that way**: all three are prefilled *from the site's own defaults*, which makes them properties of the place. They carry over, they are touched about once a trip, and they were sitting above nothing in the group a diver opens to record what the water was actually like. They get *Water & entry*, below *Conditions*; **weather leads *Conditions*** because it is the first thing anyone notices about a dive day. The general lesson is the one §4.1 keeps re-teaching one layer up: a group is a claim about what its contents *are*, and a field that carries over sitting among fields that are fresh every dive is that claim being wrong.
- **The coordinate rows come off the form** (M1i, owner's call: *"no one will ever type it manually"*). Latitude and longitude were two decimal keypads, and **§2.3 had already specified the real affordance** — "a GPS pin can be set from the map or *use my location*, pressed right on the boat" — so the form was offering a flow the plan never asked for while the flow it did ask for waited on M2. The columns stay (§6) and the dive detail still reads a point back, so this removes an input, not a capability. **The consequence is stated rather than discovered: no dive logged in M1 can carry a GPS point.** That was already true in practice — nobody types coordinates on a boat — and is now true by design, which is the difference between a gap and a defect. Worth noticing that this is the same shape as the empty state and the migration collapse: the form had a row nobody would ever use, and it survived every gate because a gate cannot ask whether a field is worth having.
- **A stored shape that cannot express a state will silently pick one, and the brief that asks for it will still read as reasonable** (M1i). The brief said "open by default is a *starting state* for a group with no remembered preference" — a sentence that presumes three states where M1h's storage held two, since a set of open ids makes *never decided* and *explicitly collapsed* the same absent row. Nothing about that is visible in the sentence, in the diff, or in a green suite; what it would have produced is a collapse that undoes itself on the next dive, **broken in the one direction nothing tested**. Found by the implementer reading the storage rather than trusting the brief, which is now the tenth such catch this session and the reason briefs get read against the code instead of executed. Two riders: the fix reads an older build's array as *"these were open, nothing was collapsed"* rather than discarding it — the faithful reading, since the old row could not hold a collapse — and **the upgrade was not theoretical**, the owner's simulator held a real M1h row that came through intact. A stored-shape migration has exactly one home; `db/settings.ts` now has a §4.1 row saying so.
- **The first dive opens every group** (M1i, owner's call). Carry-over is what makes the value rule work, and a first-time diver has none — so the rule that keeps a form quiet for an experienced diver leaves a beginner with five closed groups on the one occasion nobody knows what the form holds. An empty logbook opens everything. The reasoning is the empty state's (§0.6): the moment before there is any data is the only moment the *shape* is worth showing, and it is worth showing once. **The condition is "the logbook is empty", not "this form has no values"** — the second would also fire on an edit of an emptied dive, and on a new dive whose carry-over happened to be blank, neither of which is a first dive. A remembered collapse still wins over it, on the same reasoning it wins over `startsOpen`.
- **A working rule described as a defect is still a defect report, and this one was mine** (M1i). I told the owner that collapsing *Gas & cylinders* "can never stick — the chevron is a lie", then corrected the count to four of seven groups, and recommended inverting the precedence. He answered by restating the rule he had asked for: *"no data = collapsed, data carried = not collapsed."* That **is** the built behaviour. The mistake was reading "a collapse should persist across dives" as the obvious intent and never checking it against the rule two paragraphs above in this same document; the four-of-seven count was correct and the conclusion drawn from it was not, which is the more dangerous shape — a real measurement lending weight to a framing nobody had verified. The rider is the useful part: **"I never fill this group" was never the group memory's job**, and adding it would have been §4.1's second-owner defect built deliberately, at the owner's expense, on my recommendation. I answered it by pointing at "Fields I use"; the owner answered it by deleting "Fields I use" (below).
- **"Fields I use" is dropped from v1** (owner's call, M1i; removes a §2.2 sentence and a §3 bullet). A settings screen that hides whole form groups was in the plan from the start, and **§2.2's own rule made it redundant without anyone noticing**: a group a diver never fills holds no data, never carries, and stays collapsed on its own — the cost of an unused group is one header row, not a group. The four groups that carry looked like the exception and are not, because **the clear control is the escape hatch and it already exists**: clearing a carried field writes a real blank (§0.6, §1), so the next dive carries nothing and the group goes quiet. "I do not log buddies" is therefore said by clearing the buddy once, in the form, at the moment the diver is thinking about it — which is a better place to say it than a settings screen they would have to know to look for. The general shape is worth keeping: **a planned feature outliving its reason is invisible, because nothing fails.** This one survived two milestones of work on the exact rule that replaced it, and was caught only when I cited it as the answer to a question the rule had already answered.
- **A justification can expire without its conclusion expiring, and the two look identical in a diff** (M1k). `SectionList` was chosen in M1b for three reasons, one of which was free sticky trip headers — and M1k turned stickiness off. The choice is still right for the other two, so nothing failed, no test went red, and §4's UI row plus §10's M1b entry went on citing a feature the app switches off. Found by the implementer reading the plan against what it had just built, which is the only way this kind is ever found: **a stale reason cannot break a build, and a spec that argues for the right answer from a wrong premise is how the next revisit gets decided badly.** Both were rewritten to name what actually earns the choice — sections, grouping and headers — rather than deleted, because the expired line is evidence about how the decision was made. Third instance this milestone, after §0.6's icon sheet and the `carried ×` chip.
- **The app had two content columns and no test could see either** (M1l, owner's call). 16 for the list, 20 for the form, the dive detail and Settings; **moving every screen from 20 to 16 left all 1655 tests green.** Not one assertion in the suite touched the distance between a screen's edge and its content, which is worth stating plainly because that is the *entire* visual grammar of a left-aligned app — the number every title, row, hairline and cluster label hangs off. The divergence itself was a survivor: the 20 held room for the old `carried ×` chip's outward tap slop, M1h retired the slop, and the number stayed with a comment justifying it by pointing at another 20. **A constant outliving its reason cannot fail**, which is the same shape as "Fields I use" and the `SectionList` stickiness argument, and the third instance this milestone. Found by the owner putting Dives and Settings side by side. The gap is closed by a sweep over the stylesheet itself rather than by a screen test, because the claim is about the sheet.
- **A header line that grows toward a floating control will reach it** (M1l, found by looking). The Dives summary — `128 dives · 96 h 12 min · deepest 41.2 m` — clears the floating capsule at one dive, stops 10 pt short of it at eight, and renders *behind* it at the owner's own three-digit example. **Every one of those states passes every test**, because a `Text` that overlaps a sibling is still on screen and still says what it says. The fix reserves the capsule's height so the line wraps beneath it; reserving its width was rejected with arithmetic — 257 pt of remaining room for a line already 255 pt long is not a margin, it is the same defect one dive later. The general rule: **a floating control and a growing line are a collision waiting on data**, and the data that triggers it is a diver's hundredth dive, which no fixture has.
- **"Stop and tell me" was overridden, and the override was right** (M1l, recorded because the honest version is more useful than the flattering one). The implementer was told to stop if it found a live reason for the 20 that neither I nor the docblock had named. It found one — the dive detail deliberately contrasted a full-bleed hero at 16 with an indented cluster column at 20 — judged it descriptive rather than load-bearing, and carried on. Its reading holds: what distinguishes those two rules is *which line closes what*, not 4 pt, and that decision survived the change intact. What makes the call defensible rather than merely lucky is that it found the **counter**-precedent too, on the same screen — `detailBack`'s docblock records M1d fixing exactly this 4 px step for exactly the owner's reason. **The lesson is about the instruction, not the implementer:** "stop if you find X" assumes X is rare and decisive, and here it was neither, so obeying it would have spent a round to arrive at the same answer. Better phrasing is "if you find X, say what it defends and whether that decision survives" — which is what it did anyway.
- **Right arithmetic, wrong question** (M1m). M1l rejected capping the Dives header's width against the floating capsule by computing that 257 pt of room remained for a 255 pt line — true, and it assumed the line had to fit on one. The owner's own design sheet wraps it to two (`128 dives · 96 h 12 min ·` / `deepest 41.2 m`), with the wrap landing exactly where the capsule begins. So the alternative that got taken instead — reserving the capsule's **height** — bought its clearance out of vertical space on the one screen whose vertical spacing the owner was already measuring against the sheet, and he saw it immediately. **A calculation is only as good as the constraint it was handed**, and "must fit on one line" was never in the design; it came from the implementation. Worth pairing with §10's other measurement entries: the numbers in this project have been reliable and the questions they answered have not.
- **"The same schema lives in SQLite and Postgres" was a claim nothing checked, for five milestones** (M2a). It was written in §6 at M0 and stayed true only because one of the two halves did not exist yet. The moment it did, a column added to `src/db/schema.ts` and not to the migrations would be a **row that syncs to nowhere** — failing no test, no build and no lint, exactly like the two content insets M1l found and the sticky-header justification M1k found. `src/db/schemaParity.test.ts` now fails on drift in either direction, with legitimate differences as a hand-edited exception list rather than a loosened comparison. **Its first two versions read finished and were not**: banning `create type … as enum` did nothing against a column retyped to an enum declared elsewhere, and the allow-list that replaced it let a `timestamptz` be downgraded to `text` — which would have broken §7's ordering silently. Both were found by mutation and neither by reading.
- **The catalogue is readable by signed-in users, not by anyone holding the key** (M2a, resolving an ambiguity in §5 that had gone unnoticed since M0). "Readable by everyone" can mean every user or every caller, and the publishable key ships inside the app, so the second reading makes the whole community catalogue a public download. Closed by default because **opening it later is two statements and closing it after a scrape is impossible**, and because the app never needs it open — §2.3's autocomplete runs off the on-device copy. The owner can overturn it; the README holds the two statements.
- **A cross-language comparison inherits the stricter format, and nobody notices until the wrong side wins** (M2a, found while writing the schema, before the RPCs that would have hit it). §7 upserts by comparing `updated_at`, and on the client that is a **string** comparison. Postgres' default rendering (`2026-09-02 09:00:00+00`) and the client's (`2026-09-02T09:00:00.000Z`) sort differently, so an RPC returning the natural Postgres spelling makes last-write-wins pick the wrong device — with **no error anywhere**, on rows nobody is watching. Recorded in §7 rather than in a comment because the obligation belongs to the protocol, not to whichever function is written next.
- **A capped column tears a figure from its unit** (M1m). Capping the Dives header against the floating capsule — the right fix — produced `…deepest 41.2` above a line holding only `m`, and at the owner's own 128-dive example it split `deepest` from its number. Nothing was wrong with the cap; the fold simply lands wherever width runs out, and a line of `count · duration · depth` has a break opportunity at every space rather than only at the separators. **The design sheet's break was being read as a layout and it is a typographic rule**: figures hold together, middots give way. The general form is worth keeping, since v1 has several composed figure lines — *a measured line is a sentence to a layout engine unless you tell it which spaces are joins*.
- **A derived constant can only be derived from something that exists** (M1m; my brief's error, the fifteenth this session). I wrote "the capsule's size is already a value in the stylesheet" — true of its height, and its **width has never been a value at all**: the capsule has no `width` and no `flex`, so it is sized by its children. The implementer named the three literals it is actually made of and summed them into `actionCapsuleWidth(glyphs)`, which is better than what I asked for: the header's cap now moves on its own when §3's Map tab adds a third glyph to that capsule, and a test that renders the capsule with three glyphs fails today if it does not. **The instruction "derive it, don't type it" is only as good as the derivation available**, and checking that the source exists is the implementer's job precisely because the person writing the brief did not.
- **A pull watermark must lag the clock, and the failure it prevents is permanent** (M2b). `now()` in Postgres is transaction start, so a push that commits after a concurrent pull has taken its snapshot carries a timestamp *earlier* than the watermark that pull returned — and is therefore skipped by that device's next pull, and its next, forever. The row is not delayed; it is lost, silently, on one device only. `pull_changes` returns `now() - 1 minute` so the following pull re-reads a small overlap, which costs nothing because the upsert is idempotent. **No exact watermark is computable from inside the function** — the alternatives are a lag or per-row bookkeeping the protocol does not have — so the minute is a deliberate margin rather than a value anyone measured.
- **A helper is only a single owner if its output cannot lose a column** (M2b). `sync_row` takes `to_jsonb(row)` rather than naming columns, so a column added to a table reaches the wire without anyone remembering to add it — the shape of the schema-parity problem solved once instead of once per function. The test written to defend that then accepted the *wrong* helper for a community table, which would have shipped the catalogue with **every pin missing and nothing raised**; found by mutation. Two of the parity test's own reference extractors could likewise have returned `[]` and left the column sweep green, now floored at a minimum count. Three instances in one task of the same defect class this project keeps finding: **the check that guards the drift needs its own guard against being vacuous.**
- **Adopt the local dives; the alternative is unrecoverable** (owner's question, M2b). A diver logs four dives before signing in, then signs into an account that already holds a hundred. Adopt them, discard them, or ask? **Adopt, and say so afterwards.** The only reason the question is interesting is a borrowed or shared phone — and adopting wrongly puts four visible, deletable dives in the wrong logbook, while discarding wrongly destroys dives that exist nowhere else. Client-side UUIDs mean there is nothing to reconcile: the local rows push as new rows, the account's arrive in the pull, and nothing collides. **Asking first was rejected** — a prompt at sign-in is a wall in front of the one flow §1 promises is optional, and a diver answers it better by looking at their list than by reading a dialog. The paired half is sign-out, which **wipes the device** (owner's call): the data is on the server, and a device that keeps one person's dives after they leave is the only route by which a second account could see them.
- **`delete_account` is one statement, and that is the security argument** (M2c). It is `delete from auth.users` and nothing else: the schema's own foreign keys decide what cascades (dives, presets, certifications, profile) and what survives with authorship severed (sites, centres, suggestions). A function listing its own DELETEs would be a **second** copy of a rule the schema already states — §4.1 — and it would be the copy running as its owner with RLS bypassed, one missing `where` away from deleting everybody's. It also takes **no arguments**, so no caller can name another account. The general form is worth keeping: *when a rule already exists as data, a function that restates it is not redundancy, it is a second rule that can disagree — and here the disagreeing version is the one with no RLS.*
- **A parity check that names its subjects by hand will miss one** (M2c, found in code written two tasks earlier). `schemaParity`'s account-deletion test listed five tables by name and **omitted `profiles.id` entirely**, so that cascade could have been dropped with the suite green — which stopped being theoretical the moment `delete_account` came to depend on it. Rewritten to read every `references auth.users` column out of the schema and require each to be classified, so a seventh table cannot be forgotten. Same defect as M1j's `CARRIED_ROWS` column and M2b's vacuous extractors: **the check that guards the drift is itself a hand-maintained list unless it is made to enumerate.** Third instance in four tasks; assume the next one exists.
- **A destructive action may not be wired before the thing that makes it safe** (M2e, found by the implementer and worth more than the feature it interrupted). Sign-out wipes the device because the logbook is on the server — and connected while §7.1's push does not yet exist, the first sign-out destroys a logbook that was never uploaded, **under a confirmation dialog promising it will come back**. The port is therefore left deliberately unwired and the control refuses, saying so. **The general rule: when a safety argument names another feature, that feature is a build-order dependency, not a footnote** — and the dangerous window is exactly the interval in which the dialog's sentence is already written and its premise is not yet true. Nothing would have failed here; the sequence was mine to get wrong and it was caught by someone reading the consequence rather than the instruction.
- **A generated migration that passes every test and cannot run on a real device** (M2d, and the second time this project has been caught by the gap between a test database and a used one). `drizzle-kit` emitted `add column … not null` with no default for the dirty flags. SQLite refuses that **only on a table that already has rows** — and `createTestDb()` starts empty, so all 1852 tests were green and the migration would have failed on the first launch of any device that had ever logged a dive. Found by *running* it against a seeded database rather than reading it; the file now carries a `DEFAULT`, and both halves of the behaviour are tests. Same family as §10's empty-state entry — the branch nobody's development data reaches — and the standing lesson of §9's M1 note: **a green suite has been wrong here repeatedly, and it is wrong in exactly the places where the fixture is cleaner than reality.**
- **The compiler is a better place for "you must set this" than a test** (M2d). The dirty flag has **no Drizzle default**, so an insert that omits it does not compile — and that claim is itself made falsifiable by `@ts-expect-error` lines, which fail if the hole ever opens. Paired with two runtime rules that a type cannot express: `clearDirtyFlags` clears only rows whose `updated_at` still matches what was pushed, because an edit made *during* a push would otherwise have its flag cleared and never sync again; and it refuses an empty list, because Drizzle's `.where(undefined)` is an UPDATE over the whole table. Both are silent-loss bugs, and neither is visible in a diff.
- **"You cannot edit it" is not "you cannot use it"** (M2, my error, corrected by the owner pushing back on a conclusion rather than on the fact under it). I established that Supabase gates email-template *editing* behind custom SMTP and therefore Pro — true — and concluded that password recovery was impossible on the free tier, which is false: the default templates exist and the built-in mailer sends them. That conclusion had already been written into §5, shaped a method choice, and told the implementer to build no recovery affordance. **The tell was available and I did not take it**: a constraint discovered on one operation was generalised to a whole capability without checking the others. Worth pairing with §10's other measurement entries — the facts in this project keep being right while the question they were asked about was wrong.
- **A green suite is silent about which parent a control hangs off** (M2f). Every test in `AccountScreen.test.tsx` passed with the mode toggle floating in dead space — including one asserting all three button labels **in order**, which looks like a layout assertion and is not: render order is identical whether the control sits inside the footer or at the end of the scroll. Found by looking at the screen, as the last four layout defects in this project were. The assertion that closes it is **containment** — the footer holds both controls, the scroll holds neither, and the block spending the device's bottom inset is the one they are in — which is the part of a layout that genuinely exists in a Jest tree. The rule worth carrying: *when a test cannot see the property you care about, find the neighbouring property it can see, rather than accepting the one it happens to check.*
- **A comparison that is sound between two values from one clock stops being sound when one side starts coming from another** (M2g, and this is the sharpest thing found in M2). M2d's pull rule — take the server row when its `updated_at` is later — was correct when written, because push did not exist and every timestamp in the comparison came from the same phone. The moment `push_changes` began restamping with the *server's* clock, the same line started letting the server's echo of a row outrank an edit made on the phone after the push went out, purely because phones run behind (§7.3's own premise). **One device losing an unsent edit to an older copy of itself, taking the dirty flag with it** — no second author, no conflict, no error. Fixed by requiring the local row to be clean, which is what M2d's docblock already said it wanted and could not express with a timestamp. Look for the shape elsewhere: **it is not a bug that was introduced, it is a bug that arrived when the other half of the system did.**
- **A guard must count the world, not read the report** (M2g). Sign-out pushes and then decides whether to wipe — and it decides by counting rows still flagged dirty in SQLite, **ignoring what the push said about itself**. A push that returns success while storing nothing is precisely the failure a wipe must survive, and there is a test that does exactly that. The general form is this project's most repeated lesson pointed at runtime rather than at tests: *the report of an action is not the action, and where the cost of being wrong is destruction, look at the world instead.*
- **The trigger list was written before the state it existed to protect** (M2h). §7.5 named four triggers from M0 and none of them fires when a session arrives — and `AppState` is already `active` at launch, so there is no foreground transition either. The four were not wrong; they were written when sign-out did not erase anything, so the case they had to cover did not exist yet. The moment §7.4 gained the wipe, "a diver signs back in and looks at their list" became a state where the correct behaviour was to pull and **nothing anywhere would.** Found by an implementer asking what actually fires rather than implementing the list as given. Same family as M2g's clock finding, and the family is worth naming: **a specification written for one half of a system keeps its wording and quietly loses its coverage when the other half lands.**
- **A retry ladder is not connectivity, and saying which you have is the point** (M2h). "Connectivity restored" needs `netinfo`, a native dependency and a rebuild — so what ships is a failed cycle retried on a doubling delay, 30 s to a five-minute ceiling. It covers the case that matters and it is **later than the real trigger and blind to the difference between a lost signal and a server refusing this device**. Recorded as a substitution rather than an implementation, because the failure mode of an unlabelled stand-in is that the next reader believes the spec.
- **A guard nobody could ever have caught failing is not worth adding** (M2h, and the implementer declined the work rather than banking it). The pending indicator draws nothing at zero, so "the read has not answered yet" and "nothing is owed" render identically — a `resolved` gate would be correct, invisible, and **untestable**, since no assertion could distinguish the two outputs. Declining is right, and the reasoning is worth keeping because the opposite instinct is strong: this project has spent four milestones adding guards, and the discipline is defended by knowing when one buys nothing.
